HTTPS에서 인증서와 암호화 연결 확인하기

웹 브라우저가 주소를 알고 서버를 찾아갔다고 해서 곧바로 응답을 신뢰하는 것은 아닙니다. HTTPS를 열 때 서버를 확인하고 서로 암호화할 준비를 하는 과정의 역할을 살핍니다.

이 장을 읽고 나면

  • HTTP와 TLS가 다루는 일을 구분한다.
  • 인증서 체인, 서버 이름, 키의 소유 증명을 설명한다.
  • 표준 HTTPS 클라이언트의 검증 설정을 확인한다.

서버를 찾고, 서버인지 확인하고, 데이터를 주고받는다

HTTP는 요청과 응답의 형식을 정합니다. HTTPS는 TLS로 보호되는 연결 안에서 HTTP의 내용을 주고받습니다. 이 장은 인증서로 서버를 인증하는 일반적인 TLS 1.3 연결을 예로 듭니다. TLS는 통신 내용이 중간에 읽히거나 조용히 바뀌는 위험을 줄이고, 클라이언트가 연결한 서버를 확인할 수 있게 합니다.

TLS 1.3 핸드셰이크에서 오가는 메시지

HTTPS의 기본 포트는 TCP 443입니다. TCP 연결이 열린 뒤(1 RTT), TLS 1.3은 다음 순서로 1 RTT 만에 연결을 준비합니다(RFC 8446).

  • ClientHello: 쓸 수 있는 암호 방식 목록, 키 교환용 값(key_share), 접속하려는 서버 이름(SNI)을 보냅니다. 한 IP에 여러 사이트가 있어도 서버가 맞는 인증서를 고를 수 있게 하는 것이 SNI입니다.
  • ServerHello: 고른 방식과 서버의 key_share를 보냅니다. 두 key_share로 양쪽은 (EC)DHE 키 합의를 해서, 도청자는 모르는 같은 비밀을 각자 계산합니다. 이 비밀은 연결마다 새로 만들고 버리므로, 나중에 서버의 개인키가 유출돼도 지난 대화를 풀 수 없습니다(전방 비밀성, forward secrecy).
  • Certificate · CertificateVerify: 서버 인증서 체인과, 지금까지의 핸드셰이크 내용에 개인키로 한 서명입니다. 아래 절의 ‘키 소유’ 확인이 이것입니다.
  • Finished: 핸드셰이크 전체에 대한 확인 값입니다. 중간에서 누가 메시지를 바꿨다면 양쪽 값이 맞지 않아 실패합니다.

TLS 1.2는 같은 일에 2 RTT가 들었고, TLS 1.3은 1 RTT로 줄였습니다. 따라서 DNS 조회와 서버 처리 시간을 빼면, 새 HTTPS 연결에서 첫 응답을 받기까지 TCP 1 RTT + TLS 1 RTT + HTTP 요청·응답 1 RTT = 약 3 RTT가 걸립니다. 이전에 연결한 서버라면 저장한 키로 첫 메시지에 데이터를 함께 보내는 0-RTT 재개도 있지만, 재전송 공격에 약해 조심해서 씁니다.

유효 기간과 정책현재 시각과 사용 목적에 맞는가?인증서가 만료됐거나 용도가 달라졌다.
키 소유서버가 인증서 공개키에 대응하는 개인키를 사용할 수 있는가?TLS 핸드셰이크에 대한 서버의 증명이 확인되지 않는다.

서버 인증서(X.509 형식)에는 서버 이름과 공개키가 연결되어 있고, 발급한 인증기관(CA)의 서명이 붙어 있습니다. 보통 서버는 자기 인증서와 그것을 서명한 중간 CA의 인증서를 함께 보내고, 브라우저·운영체제에 미리 들어 있는 루트 CA 인증서까지 서명을 차례로 확인해 인증서 체인을 완성합니다. 인증서 목록을 검사한 뒤에는 서버가 그 공개키에 대응하는 개인키를 실제로 사용했다는 핸드셰이크 서명도 확인합니다. 다른 사람이 서버의 공개 인증서 파일을 가졌다는 사실만으로는 그 서버인 척할 수 없습니다. 발급기관에 대한 신뢰와 실제 연결에서 개인키를 보유했다는 증명이 함께 쓰입니다.

인증서에서 확인한 공개키와 연결마다 자료를 암호화하는 비밀 키는 역할이 다릅니다. 일반적인 TLS 연결에서는 키 합의와 키 도출을 거쳐 보호된 레코드의 대칭키가 만들어집니다. 두 쪽은 그 키로 레코드를 읽고 변경 여부를 확인합니다. 인증서 파일 자체를 HTTP 데이터를 모두 암호화하는 비밀키로 이해하면 순서가 섞입니다.

검증 기본값을 사용하는 예

Python의 표준 ssl 모듈은 서버 인증에 맞는 기본 문맥을 만들 수 있습니다. 아래 코드는 문맥의 두 설정을 표시하고 실제 네트워크에는 접속하지 않습니다. 접속이 필요한 프로그램에서는 URL의 서버 이름을 사용하고 기본 검증의 결과를 확인합니다.

import ssl

context = ssl.create_default_context()
requires_certificate = context.verify_mode == ssl.CERT_REQUIRED
print("인증서 검증:", requires_certificate)
print("호스트 이름 검증:", context.check_hostname)
assert requires_certificate and context.check_hostname

실행 결과

인증서 검증: True
호스트 이름 검증: True

서버 이름이 맞지 않거나 신뢰 경로가 없는 경우에는 연결 오류 단계에서 주소와 서버 구성을 확인합니다. 성공한 연결은 요청을 보호하지만 사이트의 모든 정보나 서비스 자체의 신뢰성을 평가해 주지는 않습니다.

한 줄 정리

TLS가 서버와 연결을 확인하고 암호화를 준비하면, 그 연결 위에서 HTTP 요청과 응답을 보호합니다.
