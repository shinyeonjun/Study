웹 주소에서 HTTP 요청과 응답 읽기

브라우저에 주소를 입력하면 어느 서버에 무슨 자료를 요청할지 정해집니다. 주소 한 줄을 조각으로 나누고, 글자로 읽기 쉬운 HTTP/1.1 예로 실제 요청과 응답의 구조를 확인합니다.

이 장을 읽고 나면

  • URL에서 스킴·호스트·포트·경로·쿼리·프래그먼트를 찾는다.
  • HTTP 요청과 응답의 첫 줄, 헤더, 본문을 구별한다.
  • 자주 만나는 상태코드를 설명한다.

URL에서 통신 상대와 원하는 자원을 찾는다

다음처럼 예시용 주소를 정합니다. https://study.example:8443/notes?page=2#table을 왼쪽부터 읽어 봅니다. URL은 웹에서 자원에 접근할 위치와 방법을 적는 표현입니다. 주소의 각 부분을 어디에서 쓰는지가 다릅니다.

부분예쓰임
스킴httpsHTTP 통신을 보호하는 연결을 쓰도록 지정
호스트study.example접속할 서버 쪽 이름
포트8443이 연결이 향하는 서버 쪽 접속 번호
경로/notes자원의 위치를 구별할 문자열
쿼리page=2페이지 번호 같은 조건을 서버에 전달
프래그먼트table받은 문서 안에서 이동할 위치 등을 브라우저가 해석

이 URL에는 포트를 따로 적었으므로 8443으로 연결을 시도합니다. 일반적인 HTTPS 주소에서 포트가 비어 있으면 기본값 443입니다. 이 장은 주소의 역할을 먼저 배우고, 연결 과정은 DNS·포트·암호화 단원에서 이어 살펴봅니다.

#table은 일반 웹 요청의 목적 문자열에 넣지 않습니다. 서버에 원하는 경로와 쿼리를 보내고, 브라우저가 응답을 읽은 뒤 스스로 table 위치를 찾을 수 있습니다.

HTTP/1.1 메시지는 어떤 줄로 나뉘나

브라우저가 예시 자료를 읽어 온다고 합시다. HTTP는 이 요청과 응답이 어떤 뜻을 갖는지 정한 웹 통신의 프로토콜입니다. 예를 들어 GET은 대상 자원의 표현을 받으려는 요청에 쓰고, POST는 요청에 담긴 데이터를 대상 자원의 규칙대로 처리하도록 요청할 때 씁니다. 이 밖에 본문 없이 헤더만 받는 HEAD, 대상 자원을 보낸 내용으로 만들거나 바꾸는 PUT, 대상 자원을 지우는 DELETE가 자주 쓰입니다. GET·HEAD는 서버 상태를 바꾸지 않는 것이 약속이고(안전한 메서드), GET·HEAD·PUT·DELETE는 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같도록 정의됩니다(멱등). POST는 둘 다 보장하지 않으므로 함부로 다시 보내면 주문이 두 번 들어가는 식의 문제가 생길 수 있습니다.

설명용으로, 위 주소의 자원에 HTTP/1.1 방식으로 보내는 메시지를 보여 줍니다. 명시한 포트를 포함한 접속 대상을 Host에 적고 Accept로 희망 응답 형식을 표시합니다.

GET /notes?page=2 HTTP/1.1
Host: study.example:8443
Accept: application/json

맨 위는 요청 줄(메서드, 요청 대상, 버전)입니다. 두 헤더 줄이 이어지고 빈 줄이 헤더의 끝을 표시합니다. 실제 HTTP/1.1에서는 각 줄 끝이 CR LF 두 바이트( )이고, 빈 줄은 하나뿐인 줄입니다. 이 GET에는 요청 본문이 없습니다. 서버는 자료를 찾아 상태코드와 응답 본문을 보낼 수 있습니다. 여기서는 JSON 문자열의 길이가 11바이트입니다.

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 11

{"count":2}

헤더는 메시지와 전달할 데이터의 형식 등에 관한 항목을 담습니다. 본문은 실제로 보내는 메시지 데이터입니다. HTTP/1.1에서는 위처럼 문자 줄을 읽어도 되지만, HTTP/2나 HTTP/3의 전송 형식은 다릅니다. 상태코드와 요청 메서드 등 HTTP가 주고받는 내용의 의미는 버전 사이에서 공통됩니다.

상태코드가 알려 주는 응답의 종류

상태코드는 세 자리 수이고 첫 자리가 종류를 정합니다. 외우기 1xx는 정보(처리 중), 2xx는 성공, 3xx는 리다이렉션(다른 곳을 보거나 보관한 것을 쓰라는 안내), 4xx는 클라이언트 오류(요청 쪽 문제), 5xx는 서버 오류(요청은 정상인데 서버가 처리하지 못함)입니다. 처음 보는 코드라도 첫 자리로 큰 뜻을 읽을 수 있습니다.

대표 코드어떤 경우인가예
200요청을 성공적으로 처리자료를 조회해 본문에 담음
204성공했으며 응답 내용 없음설정을 적용하고 별도 본문은 돌려주지 않음
304조건부 조회에서 예전 자료를 재사용 가능조건부 GET에 응답하고 브라우저는 보관한 값 사용
301자원이 영구히 다른 URL로 옮겨짐응답의 Location 헤더에 새 주소가 있어 브라우저가 따라감
400요청 형식이 잘못되어 처리할 수 없음문법이 깨진 요청
401인증 정보가 없거나 유효하지 않음로그인 토큰 없이 API 호출
403요청을 이해했지만 허용하지 않음로그인은 했지만 그 자료에 권한이 없음
404요청한 자원의 현재 표현을 찾을 수 없거나 공개하지 않음없는 장 주소를 요청
500서버에서 요청 처리를 막는 예기치 않은 조건 발생응답을 만드는 내부 프로그램 오류
503서버가 일시적으로 요청을 처리할 수 없음과부하나 점검 중

예를 들어 404가 실제 HTTP 응답으로 돌아왔다면, 브라우저는 어느 응답자에게서 HTTP 메시지를 받았습니다. ‘아무 서버에도 연결하지 못했다’는 브라우저 오류와 구분할 수 있습니다. 중간 서비스가 404를 돌려줬다면 원래 의도한 응답자와 다를 수 있습니다.

파이썬으로 주소가 잘리는 위치 확인하기

from urllib.parse import urlsplit, parse_qs

url = "https://study.example:8443/notes?page=2#table"
parts = urlsplit(url)
target = parts.path + ("?" + parts.query if parts.query else "")
print(parts.scheme, parts.hostname, parts.port)
print("target", target)
print("query", parse_qs(parts.query))
print("fragment", parts.fragment)

실행 결과

https study.example 8443
target /notes?page=2
query {'page': ['2']}
fragment table

urlsplit은 여기서 문자열을 나눠 보여 줄 뿐입니다. 서버에 연결하는 동작은 다음 장 예제에서 직접 봅니다.

한눈에 정리

  • 스킴·호스트·포트는 연결 방식과 상대를, 경로·쿼리는 접근할 자료나 조건을 고른다. 프래그먼트는 브라우저가 사용한다.
  • 요청 줄에는 메서드와 목적 문자열, 응답 줄에는 상태코드가 들어간다.
  • 헤더는 형식 등 추가 정보를 준다. 응답 본문이 없는 성공도 있다.
