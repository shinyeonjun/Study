텍스트 파일·경로·인코딩

지금까지 만든 프로그램은 끝나는 순간 모든 값을 잊었습니다. 변수는 메모리에 있고, 메모리는 프로그램이 끝나면 비워지기 때문입니다. 이 장에서는 Python으로 파일에 글을 쓰고 다시 읽는 법, 파일을 찾아가는 경로, 그리고 한국어 Windows에서 거의 반드시 한 번은 만나는 "인코딩 오류"를 실제로 일으켜 보고 고칩니다.

이 장을 읽고 나면

  • open과 with로 텍스트 파일을 쓰고, 덧붙이고, 읽을 수 있다.
  • 읽기·쓰기·덧붙이기 모드의 차이와 "w"가 위험한 이유를 설명할 수 있다.
  • 상대 경로가 어디를 기준으로 풀리는지 설명하고, 경로 때문에 나는 오류를 고칠 수 있다.
  • 인코딩이 무엇인지, UTF-8과 CP949가 같은 글자를 어떻게 다르게 저장하는지 설명할 수 있다.
  • UnicodeDecodeError를 보고 원인을 짚어 알맞은 encoding으로 고칠 수 있다.

파일을 읽고 쓰는 흐름

파일은 "이름이 붙은 데이터 덩어리"이고, 디스크에 저장되어 전원을 꺼도 남습니다. 디스크에 실제로 적히는 것은 글자가 아니라 바이트(byte), 곧 0부터 255까지의 숫자들입니다. 반면 Python 프로그램 안에서 우리는 "이름" 같은 글자(문자열)를 다룹니다. 그러니 파일에 쓸 때는 글자를 바이트로 바꾸고, 읽을 때는 바이트를 글자로 되돌리는 단계가 반드시 끼어 있습니다.

이 그림의 세 부분을 이 장에서 차례로 다룹니다. 가운데 칸을 여는 open과 닫는 with, 오른쪽 파일을 찾아가는 경로, 그리고 화살표 위의 인코딩입니다.

첫 파일 쓰고 읽기 이해하기

이 장의 코드는 모두 새 폴더(예: study\py07a)를 하나 만들어 그 안에 파일로 저장하고, 명령 프롬프트에서 그 폴더로 이동한 뒤 python 파일이름.py로 실행했습니다(폴더 이동은 cd 폴더이름). 실행 결과는 Windows 11, Python 3.14에서 실제로 나온 것입니다.

파일 01_write_read.py

with open("memo.txt", "w", encoding="utf-8") as f:
    f.write("첫째 줄\n")
    f.write("둘째 줄\n")
print("다 썼습니다")

with open("memo.txt", "r", encoding="utf-8") as f:
    text = f.read()
print(repr(text))
print(text)

실행 결과

다 썼습니다
'첫째 줄\n둘째 줄\n'
첫째 줄
둘째 줄

실행이 끝나면 폴더에 memo.txt가 생겨 있고, 메모장으로 열면 두 줄이 보입니다. 코드를 뜯어봅시다.

정의

open(파일 이름, 모드, encoding=인코딩)은 파일을 열어 파일 객체를 돌려줍니다. 파일 객체는 파일로 드나드는 문입니다. 이 문으로 f.write(문자열)(쓰기), f.read()(전부 읽기)를 합니다.

  • 파일 이름: 여는 파일의 경로. 여기서는 폴더 없이 이름만 썼으므로 "지금 폴더의 memo.txt"입니다(경로 절에서 자세히).
  • 모드: 무엇을 하려고 여는지. 아래 표.
  • encoding: 글자를 바이트로 어떻게 바꿀지. 이 교재에서는 항상 적습니다. 이유는 인코딩 절에서 실제 오류로 보여 줍니다.
모드뜻파일이 없으면파일이 있으면
"r" (생략하면 이것)읽기 readFileNotFoundError처음부터 읽는다
"w"쓰기 write새로 만든다내용을 모두 지우고 처음부터 쓴다
"a"덧붙이기 append새로 만든다원래 내용 끝에 이어 쓴다
용어 repr(x)는 값을 "코드에 적는 모양 그대로" 보여 주는 함수입니다. 줄바꿈이 \n으로, 문자열 양끝의 따옴표가 그대로 보여서 눈에 안 보이는 글자를 확인할 때 씁니다.

"\n"은 줄바꿈 글자입니다. write는 print와 달리 줄을 저절로 바꿔 주지 않으므로, 줄을 바꾸려면 \n을 직접 넣어야 합니다. repr(text)로 찍어 보니 파일 내용은 '첫째 줄\n둘째 줄\n'이라는 문자열 하나였습니다. 그냥 print(text)를 하면 \n이 실제 줄바꿈으로 보이고, 끝의 \n과 print 자신의 줄바꿈이 겹쳐 맨 아래에 빈 줄이 하나 생깁니다.

덧붙이기와 한 줄씩 읽기

파일 02_append_lines.py (01을 실행한 다음에 실행)

with open("memo.txt", "a", encoding="utf-8") as f:
    f.write("셋째 줄\n")

with open("memo.txt", encoding="utf-8") as f:
    for line in f:
        print(repr(line), "->", repr(line.strip()))

with open("memo.txt", encoding="utf-8") as f:
    lines = f.readlines()
print(lines)
print(len(lines))

실행 결과

'첫째 줄\n' -> '첫째 줄'
'둘째 줄\n' -> '둘째 줄'
'셋째 줄\n' -> '셋째 줄'
['첫째 줄\n', '둘째 줄\n', '셋째 줄\n']
3
  • "a"로 열었으므로 원래 두 줄 뒤에 셋째 줄이 붙었습니다.
  • 모드를 생략하면 "r"입니다. 그래서 둘째 open에는 모드가 없습니다.
  • for line in f:는 파일을 한 줄씩 읽습니다. 각 줄 끝에 \n이 붙어 있으므로, 내용만 쓰려면 line.strip()으로 양끝의 공백과 줄바꿈을 떼어 냅니다. 큰 파일도 한 줄씩만 메모리에 올리므로 부담이 적습니다.
  • f.readlines()는 모든 줄을 리스트로 한 번에 돌려줍니다.

흔한 실수

있는 파일을 "w"로 여는 것. "w"는 여는 순간 기존 내용을 전부 지웁니다. 아무것도 쓰지 않고 닫아도 빈 파일이 됩니다. 묻지도 않고, 휴지통에도 가지 않습니다.

파일 03_overwrite.py (02 다음에 실행)

with open("memo.txt", "w", encoding="utf-8") as f:
    f.write("새 내용\n")

with open("memo.txt", encoding="utf-8") as f:
    print(f.read())
새 내용

세 줄이 사라지고 "새 내용" 한 줄만 남았습니다. 원본 자료 파일은 읽기 전용으로만 열고, 결과는 다른 이름의 파일에 쓰는 습관을 들이세요.

읽기 모드로 없는 파일을 열면 오류가 납니다. 파일 이름을 잘못 쳤을 때(score.txt와 scores.txt), 또는 다른 폴더에서 실행했을 때 가장 자주 만납니다.

with문과 파일 닫기

문을 열었으면 닫아야 합니다. 파일 객체도 다 쓰면 f.close()로 닫아야 하는데, 닫는 일에는 두 가지 뜻이 있습니다.

  • 쓴 내용을 확실히 디스크에 내려보냅니다. write한 글자는 효율을 위해 잠시 메모리에 모아 두었다가 한꺼번에 디스크로 보내는 경우가 많습니다. 닫을 때 남은 것을 모두 보냅니다. 닫지 않은 채 프로그램이 비정상으로 끝나면 끝부분이 빠질 수 있습니다.
  • 파일을 놓아줍니다. 운영체제는 열려 있는 파일을 기억해 둡니다. 특히 Windows에서는 어떤 프로그램이 열고 있는 파일을 지우거나 이름을 바꾸지 못하는 경우가 있습니다.

정의

with open(...) as f: 아래에 들여 쓴 부분(블록)이 끝나면 파일이 자동으로 닫힙니다. 블록 안에서 오류가 나서 중간에 빠져나가도 닫힙니다. 이런 문법을 with문이라고 하며, 파일을 열 때는 언제나 이것을 씁니다.

파일 05_closed.py

f = open("memo.txt", encoding="utf-8")
print(f.closed)
f.close()
print(f.closed)

with open("memo.txt", encoding="utf-8") as g:
    print(g.closed)
print(g.closed)
g.read()

경로: 파일을 찾아가는 주소

경로는 두 가지로 나뉩니다. C:\Users\...\study\py07a\memo.txt처럼 드라이브부터 끝까지 적은 절대 경로, 그리고 data\scores.csv처럼 "어딘가를 기준으로" 적은 상대 경로입니다. Python에서 중요한 질문은 하나입니다. 상대 경로의 그 "어딘가"는 어디인가?

정의

상대 경로는 현재 작업 폴더(current working directory)를 기준으로 풀립니다. 현재 작업 폴더는 python 명령을 실행한 그 순간 명령 프롬프트가 있던 폴더입니다. .py 파일이 있는 폴더가 아닙니다.

같은 스크립트를 두 곳에서 실행해 확인해 봅시다. Path.cwd()는 현재 작업 폴더를, .resolve()는 상대 경로를 절대 경로로 풀어 보여 줍니다(아래에서 설명할 pathlib의 기능입니다).

파일 08_cwd.py

from pathlib import Path
print(Path.cwd())
print(Path("data/scores.csv").resolve())

py07a 폴더에서 python 08_cwd.py

C:\Users\...\study\py07a

스크립트는 똑같은데, 둘째 실행에서는 data\data\scores.csv라는 있지도 않은 곳을 가리킵니다. 현재 작업 폴더가 data였으니 거기에 또 data를 붙인 것입니다. 이 상태에서 파일을 열면 FileNotFoundError가 납니다. (..는 "한 단계 위 폴더"입니다.)

그래서 이 교재에서는 스크립트가 있는 폴더로 이동한 뒤 실행하는 것을 원칙으로 합니다. VS Code 같은 편집기의 "실행" 단추는 현재 작업 폴더를 다른 곳(열어 둔 작업 영역의 맨 위 폴더 등)으로 잡을 수 있으니, 경로 오류가 나면 먼저 Path.cwd()를 찍어 보세요.

pathlib으로 경로 다루기

경로를 글자로 이어 붙이다 보면 \를 빼먹거나 두 번 넣기 쉽습니다. Python에 딸려 오는 pathlib의 Path를 쓰면 경로를 조각으로 다룰 수 있습니다. from pathlib import Path는 "pathlib 묶음에서 Path를 꺼내 쓰겠다"는 줄입니다(import는 PY09에서 자세히).

첫 줄은 \n 자리에서 줄이 바뀌고 \t 자리에 탭이 들어가 엉망이 되었습니다. 고치는 법은 셋입니다. ① 따옴표 앞에 r을 붙여 날 문자열(raw string)로 만들기: 역슬래시를 글자 그대로 둡니다. ② 슬래시 /로 적기: print는 슬래시를 그대로 보여 주지만, 파일을 열 때는 Windows도 /를 경로 구분자로 받아들입니다. ③ Path 쓰기.

인코딩: 글자를 바이트로 바꾸는 약속 이해하기

그림 1의 화살표 위에서 일어나는 일입니다. 컴퓨터는 글자를 숫자로만 저장할 수 있으므로, "어떤 글자를 어떤 바이트들로 적을지" 정한 약속표가 필요합니다. 문제는 이 약속표가 하나가 아니라는 데 있습니다.

정의

인코딩(encoding): 글자를 바이트로 바꾸는 일, 또는 그 바꾸는 규칙. 디코딩(decoding): 바이트를 글자로 되돌리는 일. 쓸 때와 읽을 때 같은 규칙을 써야 원래 글자가 돌아옵니다.

  • UTF-8: 세계의 거의 모든 글자를 담는 국제 표준 규칙. 영문·숫자는 1바이트, 한글 한 글자는 보통 3바이트. 웹과 Python, macOS·Linux의 기본입니다.
  • CP949: 한국어 Windows가 예전부터 써 온 규칙(EUC-KR을 넓힌 것). 영문·숫자 1바이트, 한글 한 글자 2바이트. 한국어 글자는 담지만 다른 나라 글자 상당수는 담지 못합니다. Windows 메뉴에서는 "ANSI"라는 이름으로 보이기도 합니다.

Python에서 문자열의 .encode(규칙)는 바이트를 돌려줍니다. 결과 앞의 b'...'는 "바이트 값"이라는 표시이고, \xea는 16진수 EA인 바이트 하나입니다.

파일 09_bytes.py

print("가".encode("utf-8"))
print("가".encode("cp949"))
print(len("가나다".encode("utf-8")), len("가나다".encode("cp949")))
print(len("abc".encode("utf-8")), len("abc".encode("cp949")))

실행 결과

b'\xea\xb0\x80'
b'\xb0\xa1'
9 6
3 3

풀이 예제

"가나다"를 두 규칙으로 저장하면 몇 바이트일까요?

① UTF-8: 한글 한 글자 3바이트 × 3글자 = 9바이트
② CP949: 한글 한 글자 2바이트 × 3글자 = 6바이트
③ "abc"는 두 규칙 모두 1바이트 × 3글자 = 3바이트 (영문은 같은 바이트)

③ 때문에 영어만 있는 파일에서는 인코딩 문제가 잘 드러나지 않습니다. 한글이 들어가는 순간 차이가 납니다.

규칙이 어긋나면: 실제 오류

같은 내용을 두 규칙으로 각각 저장하고, 저장된 바이트를 그대로 들여다봅니다. "rb"는 "바이트 그대로 읽기(read binary)" 모드로, 디코딩을 하지 않습니다.

파일 10_make_files.py

with open("utf8.txt", "w", encoding="utf-8") as f:
    f.write("이름,점수\n민수,80\n")
with open("ansi.txt", "w", encoding="cp949") as f:
    f.write("이름,점수\n민수,80\n")
with open("utf8.txt", "rb") as f:
    print(f.read())
with open("ansi.txt", "rb") as f:
    print(f.read())

b'\xc0\xcc\xb8\xa7,\xc1\xa1\xbc\xf6\r\n\xb9\xce\xbc\xf6,80\r\n'

쉼표(,)와 80은 양쪽이 똑같고, 한글 부분만 다릅니다. 하나 더 보이는 것이 있습니다. 코드에서는 \n만 썼는데 파일에는 \r\n이 적혔습니다. Windows의 텍스트 파일은 줄바꿈을 \r\n 두 글자로 적는 관례가 있어서, 텍스트 모드로 쓰면 Python이 알아서 바꿔 줍니다. 읽을 때는 다시 \n으로 돌려주므로 평소에는 신경 쓸 일이 없습니다(다음 장 CSV에서 한 번 더 나옵니다).

이 예에서는 기본값이 CP949라 UTF-8 파일을 열 때 오류가 났습니다. 기본값이 UTF-8인 환경에서는 같은 코드가 성공합니다. Python 3.15부터는 UTF-8 모드가 기본이지만 설정으로 끌 수 있습니다. 파일 형식을 알고 있다면 encoding에 명시해 환경에 따라 뜻이 바뀌는 일을 피합니다.

엑셀이 만든 CSV와 BOM

엑셀에서 "CSV UTF-8" 형식으로 저장한 파일은 맨 앞에 BOM(byte order mark)이라는 3바이트 표시(EF BB BF)를 붙이는 경우가 많습니다. "이 파일은 UTF-8"이라는 꼬리표입니다. 이것을 그냥 utf-8로 읽으면 첫 글자 앞에 보이지 않는 글자 \ufeff가 붙어 나옵니다.

파일 16_bom.py

with open("excel.csv", "w", encoding="utf-8-sig") as f:
    f.write("이름,점수\n민수,80\n")
with open("excel.csv", "rb") as f:
    print(f.read()[:6])
with open("excel.csv", encoding="utf-8") as f:
    print(repr(f.readline()))
with open("excel.csv", encoding="utf-8-sig") as f:
    print(repr(f.readline()))
b'\xef\xbb\xbf\xec\x9d\xb4'
'\ufeff이름,점수\n'
'이름,점수\n'

첫 열 이름이 "이름"이 아니라 "\ufeff이름"이 되어 버리면, 나중에 row["이름"]으로 찾을 때 KeyError가 납니다. 눈에는 똑같이 보여서 찾기 어렵습니다. encoding="utf-8-sig"로 읽으면 BOM을 떼어 줍니다(BOM이 없는 파일도 문제없이 읽습니다). 한편 엑셀의 그냥 "CSV (쉼표로 분리)" 형식은 한국어 Windows에서 보통 CP949로 저장됩니다.

외우는 법

내가 쓸 텍스트 파일의 기본은 UTF-8입니다. 다른 사람이 만든 파일은 인코딩 정보를 확인합니다. UTF-8 파일에 BOM이 있다면 utf-8-sig로 읽고, CP949로 내보낸 파일이라면 cp949로 읽습니다.

왜 그럴까?

파일 안에 "나는 UTF-8이다"라고 늘 적어 두면 이런 문제가 없을 텐데, 텍스트 파일은 왜 자기 인코딩을 스스로 알려 주지 않을까요?

모범 답 보기

텍스트 파일은 "바이트를 줄줄이 늘어놓은 것" 이상의 구조가 없기 때문입니다. 어디에 꼬리표를 둘지 정해진 자리가 없고, 꼬리표를 붙이면 그것도 내용의 일부로 읽혀 버립니다. BOM이 바로 그런 시도인데, 위에서 본 것처럼 BOM을 모르는 프로그램은 그것을 이상한 글자로 읽습니다. 그래서 인코딩은 대개 파일 밖의 약속(문서, 관례, 사람 사이의 합의)으로 전해지고, 읽는 쪽이 알맞은 규칙을 골라야 합니다. 오늘날에는 "모든 곳에서 UTF-8"로 약속을 통일하는 쪽으로 가고 있습니다.

다음 장(PY07·2)에서는 이 장의 도구로 실제 자료 파일인 CSV와 JSON을 읽고 씁니다. 인코딩 오류는 PY08에서 오류 처리를 배울 때 다시 만납니다.
