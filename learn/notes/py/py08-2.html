PY08·2

예외 처리와 입력 검증

점수 입력 칸에 누군가 "팔십"이나 "105"를 넣어도 프로그램 전체가 죽어서는 안 되고, 그렇다고 그 값을 조용히 받아들여서도 안 됩니다. 이 장에서는 예외를 잡는 try/except, 일부러 예외를 일으켜 호출한 쪽으로 넘기는 raise, 입력을 단계별로 검사하는 함수, 그리고 그 함수를 경계값으로 시험하는 법을 다룹니다.

이 장을 읽고 나면

  • try/except/else/finally의 실행 순서를 코드만 보고 맞힐 수 있다.
  • except를 좁게 써야 하는 이유를 실제 예로 설명할 수 있다.
  • raise로 예외를 일으키고, 예외가 호출 스택을 따라 위로 전달되는 과정을 그릴 수 있다.
  • 문자열 입력을 단계별로 검증하는 함수를 쓸 수 있다.
  • 경계값 테스트 입력을 고르고 assert로 테스트를 작성할 수 있다.

try/except: 예외를 잡아 처리하기 이해하기

PY08·1에서 예외는 프로그램을 그 자리에서 멈추게 했습니다. 예외가 날 수 있는 줄을 try 블록에 넣고, 그 예외의 종류를 except에 적으면, 멈추는 대신 except 블록을 실행하고 이어서 진행합니다. 이 장의 실행 결과도 모두 Windows 11, Python 3.14의 실제 출력입니다.

파일 01_try.py

texts = ["85", "팔십", "90"]
for text in texts:
    try:
        score = int(text)
        print("받은 점수:", score)
    except ValueError:
        print("숫자가 아님:", text)
print("끝")

실행 결과

받은 점수: 85
숫자가 아님: 팔십
받은 점수: 90
끝

"팔십"에서 int(text)가 ValueError를 내자, try 블록의 나머지(print("받은 점수:", ...))는 건너뛰고 except ValueError: 블록으로 갔습니다. 그다음 반복은 정상적으로 계속되어 90까지 처리했습니다.

정의

try:
    예외가 날 수 있는 코드
except 예외종류 as e:
    그 종류의 예외가 났을 때 (e는 예외 객체, str(e)는 메시지)
else:
    try 블록이 예외 없이 끝났을 때만
finally:
    예외가 났든 안 났든, 블록을 떠날 때 언제나

except는 적힌 종류(와 그 하위 종류)의 예외만 잡습니다. 맞는 except가 없으면 예외는 잡히지 않고 바깥으로 전달됩니다. else와 finally는 생략할 수 있습니다. PY07·1의 with문이 파일을 "오류가 나도 닫는" 것은 finally와 같은 원리입니다.

else, finally, as e

파일 02_try_full.py

def to_score(text):
    try:
        score = int(text)
    except ValueError as e:
        print("변환 실패, 이유:", e)
        return None
    else:
        print("변환 성공")
        return score
    finally:
        print("to_score 끝:", repr(text))

print(to_score("85"))
print(to_score("abc"))

실행 결과

변환 성공
to_score 끝: '85'
85
변환 실패, 이유: invalid literal for int() with base 10: 'abc'
to_score 끝: 'abc'
None
입력실행 순서
"85"try 성공 → else("변환 성공", return 85 예약) → finally("to_score 끝") → 함수가 85를 돌려줌 → 바깥 print가 85 출력
"abc"try에서 ValueError → except(e의 메시지 출력, return None 예약) → finally → None 반환

주목할 점은 return이 있어도 finally가 먼저 실행된다는 것입니다. return은 돌려줄 값을 정해 두고, 함수를 떠나기 직전에 finally를 실행합니다. 그래서 "to_score 끝"이 85보다 먼저 찍혔습니다. as e의 e는 예외 객체이고, print하면 traceback 맨 아래 줄의 이유 부분이 나옵니다. else 블록을 따로 두는 이유는 "int 변환"에서 나는 ValueError만 잡고, 성공한 뒤의 코드에서 나는 예외까지 except가 삼키지 않게 하려는 것입니다. try 블록은 예외가 날 줄만 담도록 짧게 씁니다.

종류를 적지 않은 except:는 모든 예외를 잡습니다. 편해 보이지만 결과는 이렇습니다.

흔한 실수

except:나 except Exception:으로 "일단 다 잡기". 예상한 실패만 잡고, 예상하지 못한 예외는 그대로 터지게 둬야 버그가 보입니다. 원칙: 그 예외를 받았을 때 무엇을 할지 정해져 있는 종류만 except에 적습니다. 빈 리스트의 평균을 0으로 할지도 사실 정책 문제입니다(평균이 0점인 학생과 점수가 없는 학생은 다릅니다). 다음 절의 raise가 대안입니다.

raise: 예외를 일으켜 위로 전달하기 이해하기

int("105")는 성공합니다. 형도 값도 정수로서 문제가 없으니까요. 하지만 점수로서는 틀렸습니다. 이처럼 Python은 모르지만 우리 프로그램의 규칙으로는 잘못된 상황에서는 직접 예외를 일으킵니다.

정의

raise 예외종류("메시지")는 그 자리에서 예외를 일으킵니다. 내장 예외와 똑같이 동작하므로, 잡지 않으면 traceback을 남기고 멈추고, 호출한 쪽에서 except로 잡을 수도 있습니다. 값이 허용 범위를 벗어났으면 ValueError, 형이 틀렸으면 TypeError를 쓰는 것이 관례입니다.

예외는 호출 스택을 따라 올라간다

예외가 난 함수 안에 맞는 except가 없으면, 그 함수는 즉시 끝나고 예외는 그 함수를 부른 쪽으로 넘어갑니다. 거기에도 없으면 또 그 위로. 맨 바깥(<module>)까지 아무도 잡지 않으면 프로그램이 멈추고 traceback이 출력됩니다. 이것이 예외 전달(propagation)입니다.

파일 06_propagate.py

def parse_score(text):
    score = int(text)
    if score < 0 or score > 100:
        raise ValueError("점수는 0~100이어야 합니다: " + str(score))
    return score

def read_scores(lines):
    scores = []
    for line in lines:
        scores.append(parse_score(line))
    return scores

def main():
    lines = ["80", "105", "90"]
    try:
        scores = read_scores(lines)
        print("점수:", scores)
    except ValueError as e:
        print("입력 오류:", e)

main()

실행 결과

입력 오류: 점수는 0~100이어야 합니다: 105

"105"에서 parse_score가 예외를 일으키자 parse_score, read_scores가 차례로 즉시 끝났고(read_scores의 반복도 거기서 멈춰 "90"은 처리되지 않음), main의 try 블록에서 print("점수:", scores)도 건너뛰고 except로 갔습니다.

이 구조의 핵심은 역할 분담입니다. parse_score는 "무엇이 잘못됐는지" 알지만 사용자에게 어떻게 알릴지는 모릅니다(화면? 로그 파일? 웹 응답?). main은 그 반대입니다. 그래서 아래 함수는 raise로 알리고, 처리 방법을 아는 위쪽에서 except로 잡습니다. 중간의 read_scores처럼 처리할 방법이 없는 함수는 잡지 않고 통과시키는 것이 맞습니다.

입력 검증

바깥에서 들어온 문자열(키보드 입력, CSV 칸, 웹 요청)을 프로그램 안으로 들이기 전에 규칙에 맞는지 확인하는 일을 입력 검증(input validation)이라고 합니다. 점수 하나를 받는 함수를 단계별로 짭니다.

파일 09_validate.py

def parse_score(text):
    text = text.strip()
    if text == "":
        raise ValueError("점수가 비어 있습니다")
    try:
        score = int(text)
    except ValueError:
        raise ValueError("정수가 아닙니다: " + repr(text))
    if score < 0 or score > 100:
        raise ValueError("0~100 밖입니다: " + str(score))
    return score

cases = ["-1", "0", "1", "99", "100", "101", "", "  85 ", "85.5", "abc"]
for text in cases:
    try:
        print(repr(text), "->", parse_score(text))
    except ValueError as e:
        print(repr(text), "-> 거부:", e)

'-1' -> 거부: 0~100 밖입니다: -1
'0' -> 0
'1' -> 1
'99' -> 99
'100' -> 100
'101' -> 거부: 0~100 밖입니다: 101

설계에서 볼 것:

  • 순서: 정리(strip) → 존재(비었나) → 형(정수인가) → 범위. 앞 단계가 뒤 단계의 전제입니다. 빈 칸을 따로 거르는 이유는 "비어 있음"과 "정수 아님"이 다른 문제이고 메시지도 달라야 하기 때문입니다(PY07·2의 하준).
  • 거부하고 이유를 말한다: 잘못된 값을 0이나 None으로 바꿔 받아들이지 않고, 무엇이 왜 틀렸는지를 담은 ValueError를 일으킵니다. 어떻게 처리할지는 호출한 쪽(위 for문의 except)이 정합니다.
  • 규칙은 명시적으로: "85.5"를 거부한 것은 "점수는 정수"라는 규칙을 정했기 때문입니다. 소수 점수를 허용할지는 요구 사항이 정합니다. 검증 함수는 그 규칙을 코드로 적어 둔 문서이기도 합니다.

경계값 테스트 외우기

앞 실행에서 일부러 고른 입력을 다시 보세요. -1, 0, 1, 99, 100, 101. 허용 범위 [0, 100]의 양 끝과 그 바로 바깥·안쪽입니다. 범위 비교 버그(<와 <=를 헷갈리는 것)는 거의 언제나 경계에서만 드러나기 때문입니다.

정의

경계값 분석(boundary value analysis): 입력 범위의 경계 값, 경계 바로 안쪽, 경계 바로 바깥을 테스트 입력으로 고르는 기법. 같은 결과를 내리라 기대되는 입력 묶음(동등 분할: 범위 안 정수, 범위 밖 정수, 정수가 아닌 글자, 빈 칸 …)마다 대표값 하나씩과 함께 씁니다. 정보처리기사에서 본 블랙박스 테스트 기법과 같은 것입니다.

경계에서만 드러나는 버그의 실제 예입니다. "60점 이상 합격"을 이렇게 짰다고 합시다.

검증 함수의 테스트 묶음

parse_score에 대한 기대를 assert로 고정해 둡니다. "거부해야 한다"를 검사하려면 예외가 나는지 확인하는 작은 함수가 필요합니다.

파일 10_boundary_tests.py (parse_score 정의는 09와 같음)

def parse_score(text):
    text = text.strip()
    if text == "":
        raise ValueError("점수가 비어 있습니다")
    try:
        score = int(text)
    except ValueError:
        raise ValueError("정수가 아닙니다: " + repr(text))
    if score < 0 or score > 100:
        raise ValueError("0~100 밖입니다: " + str(score))
    return score

def rejects(text):
    try:
        parse_score(text)
    except ValueError:
        return True
    return False

assert parse_score("0") == 0
assert parse_score("100") == 100

왜 그럴까?

parse_score가 잘못된 입력에 예외를 일으키는 대신 None을 돌려주게 만들면 무엇이 나빠질까요?

모범 답 보기

세 가지가 나빠집니다. ① 호출한 쪽이 None 확인을 잊으면 None이 리스트에 섞여 들어가고, 한참 뒤 sum()에서 TypeError가 나서 원인과 먼 곳에서 터집니다(PY08·1의 "원인 값이 어디서 왔나" 추적이 길어짐). ② "비어 있음", "정수 아님", "범위 밖"이라는 이유가 None 하나로 뭉개집니다. ③ 중간 함수(read_scores)마다 None을 확인하고 전달하는 코드를 써야 합니다. 예외는 확인을 잊으면 즉시 멈추고, 이유를 메시지로 담고, 중간 함수를 그냥 통과해 처리할 수 있는 곳까지 올라갑니다.

이 장의 패턴(검증 함수 + raise + 위에서 except + 경계값 assert)은 DA06에서 데이터 품질을 점검할 때, DB06·NW09에서 외부 데이터와 네트워크 오류를 다룰 때, RS04에서 실험 코드를 검산할 때 그대로 다시 씁니다.

한눈에 정리

도구핵심
try/excepttry의 예외 중 적힌 종류만 잡는다. 맞는 except가 없으면 위로 전달. as e로 예외 객체
else / finallyelse: 예외 없을 때만. finally: 언제나(return 전에도)
좁은 exceptexcept:는 NameError 같은 버그까지 숨긴다. 처리법이 정해진 종류만 잡는다
raise규칙 위반을 예외로 알린다(범위 → ValueError, 형 → TypeError). raise 단독은 잡은 예외를 다시 올림
예외 전달잡을 때까지 호출 스택을 거슬러 올라간다. 아래는 raise, 처리법을 아는 위에서 except
입력 검증정리 → 존재 → 형 → 범위 순서. 거부하고 이유를 말한다. assert가 아니라 raise로
경계값 분석경계, 바로 안쪽, 바로 바깥 + 동등 분할의 대표값. assert로 테스트를 남긴다

한 줄 정리

잘못된 입력은 검증 함수가 raise로 거부하고, 예외는 처리법을 아는 위쪽에서 좁은 except로 잡으며, 그 동작은 경계값 테스트로 고정한다.
