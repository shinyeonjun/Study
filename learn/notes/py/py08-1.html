PY08·1

오류 읽기·재현·assert

예외로 멈춘 프로그램이 남기는 여러 줄의 기록은 "어디서, 무엇 때문에 멈췄는지"를 정확히 적은 보고서입니다. 이 장에서는 그 보고서(traceback)를 아래에서부터 읽는 법, 오류를 일부러 다시 일으켜 범위를 좁히는 법, 그리고 오류 없이 틀린 답을 내는 코드를 assert로 붙잡는 법을 배웁니다.

이 장을 읽고 나면

  • 문법 오류, 실행 중 오류(예외), 논리 오류를 구분할 수 있다.
  • traceback을 아래에서 위로 읽어 오류의 종류, 일어난 줄, 원인이 된 호출을 찾을 수 있다.
  • 자주 나오는 오류 이름(NameError, TypeError, ValueError, IndexError, KeyError 등)을 보고 원인을 짐작할 수 있다.
  • 오류를 같은 입력으로 다시 일으키고, 입력을 줄여 가장 작은 재현을 만들 수 있다.
  • assert로 "이래야 한다"는 검사를 코드에 남기고, 그 한계를 설명할 수 있다.

오류의 세 종류

프로그램이 기대와 다르게 움직이는 것을 버그(bug), 버그를 찾아 고치는 일을 디버깅(debugging)이라고 합니다. 버그가 드러나는 모습은 크게 세 가지입니다. 어느 쪽인지에 따라 찾는 방법이 다르므로 먼저 구분합니다.

정의

문법 오류(SyntaxError): Python의 문법 규칙에 맞지 않아 실행을 시작하기도 전에 거절되는 오류. 쌍점(:)·괄호 빠뜨리기, 들여쓰기 틀리기 등.
예외(exception): 문법은 맞지만 실행하다가 더 이상 진행할 수 없는 상황(0으로 나누기, 없는 키 찾기 등)이 생겨 그 자리에서 멈추는 오류. 실행 중 오류라고도 합니다.
논리 오류: 오류 메시지 없이 끝까지 실행되지만 결과가 틀린 경우. 컴퓨터는 이것이 틀린 줄 모릅니다.

(가)를 실제로 확인해 봅니다. 1번 줄의 print는 문법이 맞는데도 실행되지 않았습니다. 이 장의 모든 결과는 Windows 11, Python 3.14에서 실제로 실행한 것입니다(파일 경로 앞부분은 C:\Users\...로 줄였습니다).

"시작"이 찍히지 않았습니다. Python은 파일 전체를 먼저 읽어 문법을 검사하고, 통과해야 1번 줄부터 실행합니다. 문법 오류에는 "Traceback" 줄도 없습니다. 아직 아무것도 실행하지 않았기 때문입니다. 메시지 expected ':'(쌍점이 와야 한다)와 ^ 표시가 고칠 자리를 정확히 가리킵니다.

외우는 법

디버깅 네 걸음: ① 재현한다(같은 입력으로 같은 오류) → ② 좁힌다(print로 어디까지 됐나, 입력 줄이기) → ③ 최소 재현을 만든다 → ④ 고친 뒤 같은 재현으로 확인한다. ④를 빼먹으면 "고친 것 같다"로 끝나기 쉽습니다.

더 알아보기 · 남에게 질문할 때

선생님이나 인터넷 게시판에 질문할 때도 최소 재현을 보냅니다. ① 짧은 코드 전체, ② traceback 전체(사진이 아니라 글자로 복사), ③ 기대한 결과와 실제 결과, ④ Python 버전과 운영체제. 이 네 가지가 있으면 다른 사람도 같은 오류를 재현할 수 있습니다. 붙이기 전에 경로 속 사용자 이름 같은 개인 정보는 지웁니다.

오류 없이 틀린 답: 논리 오류 찾기

더 까다로운 버그는 아무 메시지 없이 틀린 답을 내는 것입니다. 평균 함수를 손으로 짜다가 이렇게 썼다고 합시다.

파일 13_bug_avg.py

def average(scores):
    total = 0
    for i in range(1, len(scores)):
        total = total + scores[i]
    return total / len(scores)

print(average([80, 90, 70]))
53.333333333333336

오류는 없습니다. 이게 틀렸다는 것을 알려면 답을 미리 손으로 계산해 두어야 합니다.

① 기대값: (80 + 90 + 70) ÷ 3 = 240 ÷ 3 = 80
② 실제 출력: 53.333…
③ 다르다 → 논리 오류

중간 값을 찍어 어디서 어긋나는지 봅니다.

파일 14_bug_avg_print.py

def average(scores):
    total = 0
    for i in range(1, len(scores)):
        total = total + scores[i]
        print("i =", i, "더한 값 =", scores[i], "total =", total)
    return total / len(scores)

print(average([80, 90, 70]))
i = 1 더한 값 = 90 total = 90
i = 2 더한 값 = 70 total = 160
53.333333333333336
반복iscores[i]total (실제)total (기대)

2회270160170
3회없음--240

i가 0부터가 아니라 1부터 시작해서 첫 점수 80을 빠뜨렸습니다. 결과는 160 ÷ 3 = 53.33…입니다. range(1, n)은 1부터 n−1까지라는 점이 원인입니다. range(len(scores))로 고치면 0, 1, 2를 돕니다. 이렇게 처음이나 끝을 하나 빠뜨리거나 하나 더 도는 실수를 하나 차이 오류(off-by-one error)라고 부르며, 매우 흔합니다.

assert: "이래야 한다"를 코드로 이해하기

방금 우리는 "average([80, 90, 70])은 80이어야 한다"를 머리로 확인했습니다. 이 기대를 코드에 적어 두면, 실행할 때마다 컴퓨터가 대신 확인해 줍니다.

정의

assert 조건, "메시지"는 "이 조건은 반드시 참이어야 한다"는 단언(assertion)입니다. 조건이 참이면 아무 일도 없이 다음 줄로 가고, 거짓이면 그 자리에서 AssertionError를 내고 멈춥니다. 메시지는 생략할 수 있습니다.

파일 15_assert_avg.py

def average(scores):
    total = 0
    for i in range(1, len(scores)):
        total = total + scores[i]
    return total / len(scores)

assert average([80, 90, 70]) == 80, "평균 계산이 틀림"
print("검사 통과")
Traceback (most recent call last):
  File "C:\Users\...\study\py08a\15_assert_avg.py", line 7, in <module>
    assert average([80, 90, 70]) == 80, "평균 계산이 틀림"
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError: 평균 계산이 틀림

조용히 53.33을 내던 논리 오류가, 이제는 시끄러운 예외가 되었습니다. 논리 오류를 예외로 바꿔서 traceback으로 위치를 알 수 있게 한 것입니다. 이렇게 "이 입력이면 이 결과"를 assert로 적은 것을 작은 테스트라고 부릅니다.

assert는 함수 안에도 둘 수 있습니다. "이 함수는 빈 리스트를 받으면 안 된다"는 약속을 적어 두는 것입니다.

파일 16_assert_inside.py

def average(scores):
    assert len(scores) > 0, "빈 목록의 평균은 구할 수 없음"
    return sum(scores) / len(scores)

print(average([80, 90, 70]))
assert average([80, 90, 70]) == 80
assert average([100]) == 100
assert average([0, 0]) == 0
print("검사 3개 통과")
print(average([]))

세 검사(평범한 값, 값이 하나, 모두 0)는 통과했고, 빈 리스트에서는 ZeroDivisionError 대신 뜻이 적힌 AssertionError가 났습니다. 오류 메시지가 "0으로 나눔"이 아니라 "빈 목록이라 안 됨"이라 원인을 바로 알 수 있습니다. 80.0 == 80처럼 실수와 정수가 같은 값이면 ==는 True입니다.

흔한 실수

assert로 사용자 입력이나 파일 내용을 검사하는 것. assert는 끌 수 있습니다. python -O 파일.py처럼 -O(최적화) 옵션으로 실행하면 assert 줄은 통째로 무시됩니다. 위 16번 파일을 그렇게 실행한 실제 결과입니다.

2번 줄의 assert가 건너뛰어져 3번 줄에서 ZeroDivisionError가 났습니다. 그래서 assert는 "내 코드가 맞다면 절대 일어나지 않을 일"을 확인하는 데만 씁니다. 사용자가 잘못 넣을 수 있는 값은 assert가 아니라 if와 raise로 검사해야 하며, 그 방법은 다음 장에서 배웁니다.

흔한 실수

실수(소수) 계산 결과를 ==로 검사하는 것. 컴퓨터는 0.1 같은 수를 2진수로 정확히 담지 못해 아주 작은 오차가 생깁니다.

파일 17_float_eq.py

import math
print(0.1 + 0.2)
print(0.1 + 0.2 == 0.3)
print(math.isclose(0.1 + 0.2, 0.3))
0.30000000000000004
False
True

실수 결과는 assert math.isclose(결과, 기대값)처럼 "충분히 가까운가"로 검사합니다.

왜 그럴까?

논리 오류보다 예외(프로그램이 멈추는 오류)가 오히려 "고마운" 오류라고들 합니다. 왜 그럴까요?

모범 답 보기

예외는 멈추는 순간 어디서 무엇 때문에 문제가 났는지 traceback으로 알려 주기 때문입니다. 논리 오류는 조용히 틀린 값을 내고 지나가서, 그 값이 보고서나 다음 계산에 섞여 들어간 뒤에야, 또는 영영 발견되지 않을 수 있습니다. 그래서 좋은 코드는 이상한 상황에서 일부러 일찍, 크게 멈추도록 만듭니다. assert와 다음 장의 raise가 바로 그 도구입니다.

다음 장(PY08·2)에서는 예외를 잡아서 처리하는 try/except, 일부러 예외를 일으키는 raise, 그리고 입력 검증과 경계값 테스트를 다룹니다. PY09에서 환경을 꾸리고 RS04에서 실험을 재현할 때도 이 장의 "재현" 생각이 그대로 쓰입니다.

한눈에 정리

주제핵심
오류의 세 종류문법 오류(실행 전 멈춤) · 예외(실행 중 그 줄에서 멈춤, traceback) · 논리 오류(멈추지 않고 답이 틀림)
traceback 읽기맨 아래 줄(종류: 이유) → 바로 위 칸(일어난 줄) → 위로 올라가며 원인 값이 온 곳. 가장 최근 호출이 마지막
오류 이름NameError 이름 · TypeError 형 · ValueError 값 · IndexError 자리 번호 · KeyError 키 · ZeroDivisionError 0 나누기
재현재현 → print로 좁히기 → 최소 재현 → 고친 뒤 같은 재현으로 확인
논리 오류기대값을 손으로 먼저 계산, 중간 값 출력, 하나 차이 오류 의심
assert조건이 거짓이면 AssertionError. 작은 테스트·내부 약속용. -O로 꺼지므로 입력 검사에는 쓰지 않는다. 실수는 math.isclose

한 줄 정리

traceback은 아래에서 위로 읽고, 버그는 먼저 재현해 최소 재현까지 좁히며, "이래야 한다"는 기대는 assert로 코드에 남긴다.
