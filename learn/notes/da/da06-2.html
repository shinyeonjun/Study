관측 시점과 데이터 누출

오늘 오전 9시에 오늘의 주문량을 예상한다고 합시다. 마감 뒤 만든 파일에는 정오 실제 기온과 최종 주문 수까지 한 행에 들어 있습니다. 파일만 보면 쓸 수 있는 숫자처럼 보이지만, 오전 9시에는 아직 없었습니다. 예측 시점과 정보가 도착한 시점을 나눠 봅니다.

이 장을 읽고 나면

  • 값이 생긴 때와 실제로 쓸 수 있게 된 때를 나눠 기록한다.
  • 정답이나 미래에만 알 수 있는 정보가 입력에 섞이는 예를 찾는다.
  • 시간순으로 학습·평가를 나눈 뒤 학습 기준으로 두 자료를 처리한다.

파일을 받은 날짜와 예측하는 순간을 구분한다

6일 모두 지난 뒤 표를 펼치면 자료가 꽉 차 있습니다. 실제 업무를 흉내 내어 비교하려면 시간을 과거로 돌려 각 날 09:00에 무엇을 알았는지 따져야 합니다. 예측 시점은 입력을 확정하고 예측을 내리는 순간입니다. 예에서 정답 자료(target)는 18:00에 확정한 그날 주문 수이고, 입력 자료(feature)는 09:00까지 정해진 변수입니다. 정답은 학습과 채점에 필요하지만, 그날의 입력 열에는 두지 않습니다.

후보 열언제 알 수 있나09:00 입력으로?
어제 최종 주문 수어제 18:00 확정예. 오늘 예측 전에 확인했다면 사용.
오늘 정오에 대한 기온 예보오늘 08:50 발표예. 실제로 당시 받은 예보를 저장해 사용.
오늘 정오 실제 기온오늘 12:00 이후아니요. 09:00에는 아직 관측되지 않았다.
08:30에 잰 재고오늘 09:10 분석 시스템 도착아니요. 잰 시각이 먼저여도 그때 시스템에 없었다.
오늘 최종 주문 수오늘 18:00 확정입력으로는 제외. 예측과 비교하는 정답 열이다.

기온 예보에 ‘정오’라는 이름이 붙어도 예보를 받아 둔 시각은 앞설 수 있습니다. 반대로 08:30에 잰 자료가 09:10에야 도착할 수도 있습니다. 행마다 사건 시각과 처음 사용할 수 있었던 시각을 따로 두면 이 차이를 확인할 수 있습니다. 역사 데이터를 며칠 뒤 수정한 값은 최초 시점에는 없었을 수 있으므로, 가능하면 당시의 파일이나 버전 기록을 보존합니다.

오전 9시에 보이는 열을 코드로 고르기

이 실습은 시간대가 모두 한국 시각(+09:00)이라고 가정합니다. datetime.fromisoformat으로 시각 문자열을 비교 가능한 객체로 바꾸고, 사용 가능 시각이 09:00 이전 또는 같은 값만 고릅니다. 09:00에 입수한 값을 예측 전에 확인할 수 있다는 계약을 가정한 예라 <=를 씁니다. 실제 업무에서 시각이 같을 때 순서가 불분명하면 엄밀한 도착 기록을 확인하거나 안전한 간격을 둡니다.

from datetime import datetime

cutoff = datetime.fromisoformat("2026-11-05T09:00:00+09:00")
fields = [
    ("어제 주문 수", "2026-11-04T18:00:00+09:00"),
    ("정오 기온 예보", "2026-11-05T08:50:00+09:00"),
    ("정오 실제 기온", "2026-11-05T12:01:00+09:00"),
    ("오전 재고", "2026-11-05T09:10:00+09:00"),
    ("오늘 주문 수", "2026-11-05T18:00:00+09:00"),
]
available = [
    name for name, time in fields
    if datetime.fromisoformat(time) <= cutoff
]
print("입력:", ", ".join(available))
print("제외:", ", ".join(name for name, _ in fields if name not in available))
입력: 어제 주문 수, 정오 기온 예보
제외: 정오 실제 기온, 오전 재고, 오늘 주문 수

예측할 때 쓸 수 없는 정보를 가져오면 데이터 누출(data leakage)이 일어납니다. 정답을 입력 열에 그대로 두는 것이 가장 눈에 잘 띄는 경우입니다. ‘최종 주문 수 × 1.05로 만든 예상 수수료’처럼 정답에서 계산한 열을 쓰는 경우에도 누출이 발생합니다. 이 열의 원래 출처와 기록 시각은 무엇인가?를 물으면 이름만으로 숨겨진 정보를 찾기 쉽습니다.

미래에 써 볼 문제면 과거부터 나눈다

각 날 09:00에 확인한 오전 기온을 새 입력 예로 씁니다. 첫 4일로 기준을 정하고 이어지는 2일로 성능을 확인한다고 합시다. 날짜를 마구 섞으면 뒤 날짜의 상황을 본 뒤 앞 날짜를 예측하는 과제가 될 수 있습니다. 시간순 분리에서는 먼저 날짜로 나누고, 학습 구간의 정답도 평가 예측을 시작할 때 이미 확정된 것만 씁니다. 이 사례는 매일 18:00에 그날 정답이 확정되므로, 4일의 마감 뒤 5일 09:00에 평가를 시작할 수 있습니다.

학습 자료에서 평균·표준편차를 계산하여 학습과 평가에 공통으로 적용합니다. 전처리 규칙에 숫자를 맞추는 활동을 적합(fit), 정해진 값을 실제 자료에 쓰는 활동을 변환(transform)이라고 합니다. 평가 자료에서 계산한 중앙값으로 결측을 채우거나, 전체 기간의 평균으로 표준화하면 평가 값을 미리 본 셈입니다. 기술 통계가 목적이어서 전체 기간을 요약하는 상황과 예측 성능을 가늠하는 상황을 구별합니다.

from statistics import mean, pstdev

observations = [
    ("2026-11-01", 18), ("2026-11-02", 18),
    ("2026-11-03", 22), ("2026-11-04", 22),
    ("2026-11-05", 26), ("2026-11-06", 28),
]
first_eval_day = "2026-11-05"
train = [temp for day, temp in observations if day < first_eval_day]
evaluation = [temp for day, temp in observations if day >= first_eval_day]
center = mean(train)
scale = pstdev(train)
assert scale > 0
print(f"학습 {len(train)}일, 평가 {len(evaluation)}일")
print(f"평균 {center:.1f}, 표준편차 {scale:.1f}")
print("평가 z:", [(temp - center) / scale for temp in evaluation])
학습 4일, 평가 2일
평균 20.0, 표준편차 2.0
평가 z: [3.0, 4.0]

예제의 날짜는 모두 YYYY-MM-DD 고정 길이 문자열이라 문자 순서가 날짜 순서와 같습니다. 다른 날짜 표기나 시간대가 섞이면 실제 날짜·시각으로 변환해 비교합니다. 기온 26℃와 28℃의 z가 모두 큰 것은 더 따뜻한 날이 뒤에 왔기 때문입니다. 학습 구간과 다른 상황에서도 예측이 통하는지는 그때 얻은 정답과 비교해야 알 수 있습니다.

정답 확정 지연과 반복 기록을 살펴본다

예를 들어 ‘앞으로 7일 안에 돌아오는 고객’을 예측하면 4일 시점의 정답을 알기 위해 11일까지 기다려야 합니다. 5일 시작 시점으로 평가 상태를 재현하려면 4일 행을 그 시점의 학습 정답으로 쓰면 안 됩니다. 관측일뿐 아니라 정답을 확인할 수 있는 날도 자르고, 필요한 경우 학습 끝과 평가 시작 사이에 간격을 둡니다. 구체적인 분리 방식은 예측 업무와 자료 주기에 맞춥니다.

같은 고객의 여러 행에서 앞 행이 나중 행과 거의 같은 사본이라면, 행 단위로 무작위로 나눌 때 같은 고객의 행이 학습과 평가 양쪽에 들어가 성능이 과대평가될 수 있습니다. 아직 만난 적 없는 고객에 대한 예측이 목표라면 고객 단위로 분리하는 것도 고려합니다. 한 사람의 과거 행동을 활용해 그 사람의 미래를 예측하는 등 실제 목표가 다르면, 언제 어떤 과거 기록을 사용할지 명확히 정합니다.
