DB11·1

충돌 그래프로 직렬화 순서를 찾고 스냅샷의 한계를 계산하기

두 거래가 서로 다른 순서로 같은 정보를 읽고 바꿉니다. 겹쳐 진행해도 한 거래씩 끝낸 결과로 설명할 수 있는지, 읽은 값과 쓰기의 앞뒤를 찾아봅니다.

이 장을 읽고 나면

  • 같은 항목에 읽기·쓰기가 섞일 때 충돌 간선을 구성한다.
  • 충돌 직렬 가능성과 위상 순서 관계를 증명한다.
  • 여러 버전에서 공통 조건이 깨지는 쓰기 비대칭 사례를 계산한다.

같은 값에 앞선 연산이 다음 연산에 영향을 줄 수 있다

한 버전의 표에 대한 연산 순서를 먼저 생각합니다. 서로 다른 트랜잭션의 두 연산이 같은 항목을 보고 적어도 하나가 쓰기라면 충돌입니다. 앞 연산의 트랜잭션에서 뒤 연산의 트랜잭션으로 간선을 긋습니다. 서로 다른 항목을 다루거나 둘 다 읽으면 이 모형에서는 둘의 순서를 바꿔도 충돌을 바꾸지 않습니다.

실행 순서x에서 생긴 간선y에서 생긴 간선
r₁(x), r₂(y), w₁(y), w₂(x)T₁→T₂T₂→T₁
r₁(x), w₁(y), r₂(y), w₂(x)T₁→T₂T₁→T₂

충돌 직렬 가능이란 모든 충돌 쌍의 순서를 유지한 채 트랜잭션을 하나씩 실행한 순서를 찾을 수 있다는 뜻입니다. 찾을 수 있다면 그 순서가 모든 그래프 간선을 지켜야 하므로 순환은 없어야 합니다. 반대로 비순환이면 위상 순서가 있어 그 순서대로 트랜잭션 각각을 통째로 실행할 때 각 충돌의 앞뒤가 원래와 같습니다. 이 조건에서는 첫 예는 불가능, 두 번째는 T₁을 먼저 두면 가능합니다.

2단계 잠금은 순환을 실행 중에 막는다

그래프를 실행 뒤에 검사하는 대신, 실행 중에 순환이 생길 수 없게 만드는 대표 규약이 2단계 잠금(2PL)입니다. 읽기 전에는 공유 잠금(S), 쓰기 전에는 배타 잠금(X)을 얻고, S끼리만 함께 쥘 수 있습니다. 각 트랜잭션은 잠금을 얻기만 하는 확장 단계 뒤에 풀기만 하는 축소 단계로 넘어가며, 한 번이라도 잠금을 풀었다면 새 잠금을 얻지 않습니다. 2PL을 지킨 스케줄은 항상 충돌 직렬 가능합니다. 각 트랜잭션이 잠금을 모두 얻은 시점(잠금 지점) 순서로 나열하면 모든 충돌 간선이 그 순서를 따르기 때문입니다. 실제 DB는 X 잠금을 커밋까지 쥐는 엄격한 2PL을 써서 커밋되지 않은 값을 다른 트랜잭션이 읽는 일(연쇄 중단)도 막습니다.

첫 스케줄 r₁(x), r₂(y), w₁(y), w₂(x)를 2PL로 실행해 봅니다. T₁이 S(x), T₂가 S(y)를 얻습니다. w₁(y)는 X(y)가 필요한데 T₂가 S(y)를 쥐고 있어 기다리고, w₂(x)는 X(x)가 필요한데 T₁이 S(x)를 쥐고 있어 기다립니다. 서로 기다리는 교착이 생기므로 DB는 하나를 중단시키고, 비직렬 스케줄은 실제로 완료되지 않습니다. 2PL은 직렬 가능성을 보장하는 대신 교착 탐지나 예방이 필요합니다.

스냅샷을 따로 읽으면 공통 규칙을 각각 깰 수 있다

MVCC는 값을 여러 버전으로 가지고 어떤 시점의 버전이 한 거래에 보일지 다루는 방식입니다. 스냅샷 격리(SI)에서 각 거래는 시작 시점에 커밋된 버전만 읽습니다. 두 동시 거래가 같은 항목을 쓰면 먼저 커밋한(또는 먼저 갱신한) 쪽만 성공하고 다른 쪽은 중단되므로 잃어버린 갱신은 막힙니다. 그러나 두 거래가 과거의 같은 상태를 보면서 서로 다른 항목만 쓰면 둘 다 커밋할 수 있습니다. 이때 같은 행을 동시에 쓰는 충돌이 없어도 두 판단이 함께 공통 조건을 깨뜨릴 수 있습니다.

초기 x=y=1입니다. T₁은 x=1일 때만 y=0으로 쓰고, T₂는 y=1일 때만 x=0으로 씁니다. 두 트랜잭션이 같은 시간의 (1,1)을 읽으면 각각 다른 항목을 0으로 만들어 둘 다 0이 될 수 있습니다. 어느 쪽을 먼저 끝내더라도 뒤 거래는 상대가 0임을 읽어 더는 쓰지 않으므로 직렬 실행은 이 결과를 만들지 않습니다. 이런 형태를 쓰기 비대칭(write skew)이라고 합니다. 연산 순서로 쓰면 r₁(x), r₂(y), w₁(y), w₂(x)로, 1절의 첫 스케줄과 같은 모양입니다. 충돌 그래프에 순환이 있지만 쓰는 항목이 달라 SI의 같은 항목 쓰기 검사에는 걸리지 않습니다.

다중 버전에서 거래가 실제로 읽은 값을 사용하려면 버전과 읽기 의존성까지 고려해야 합니다. 한 버전의 위 충돌 그래프를 보이는 것만으로 스냅샷 검사의 동작을 구현할 수는 없습니다. PostgreSQL에서 REPEATABLE READ 수준은 스냅샷 격리로 구현되어 이 쓰기 비대칭을 허용합니다. SERIALIZABLE 수준은 스냅샷 격리 위에 거래 사이의 읽기-쓰기 의존을 추적하는 직렬화 가능 스냅샷 격리(SSI)를 써서, 위험한 의존 구조가 생기면 한 거래를 직렬화 실패(SQLSTATE 40001)로 중단시킵니다. 응용은 그 거래를 다시 실행해야 합니다.

from itertools import permutations

def edges(history):
    return {(a,b) for i,(a,kind,x) in enumerate(history)
            for b,mode,y in history[i+1:]
            if a!=b and x==y and "w" in (kind,mode)}

a = [(1,"r","x"),(2,"r","y"),(1,"w","y"),(2,"w","x")]
b = [(1,"r","x"),(1,"w","y"),(2,"r","y"),(2,"w","x")]
for history in (a,b):
    graph=edges(history)
    orders=[o for o in permutations((1,2))
            if all(o.index(i)<o.index(j) for i,j in graph)]
    print(sorted(graph),orders)

def apply(state,transaction):
    x,y=state
    if transaction==1 and x==1:
        return x,0
    if transaction==2 and y==1:
        return 0,y
    return state

initial=(1,1)
_,y=apply(initial,1)
x,_=apply(initial,2)
print((x,y), apply(apply(initial,1),2),apply(apply(initial,2),1))

한눈에 정리

핵심어기억할 기준
충돌다른 트랜잭션, 같은 항목, 적어도 하나가 쓰기. 앞 연산의 트랜잭션에서 뒤로 간선을 긋습니다.
충돌 직렬 가능충돌 그래프가 비순환일 때와 동치이며, 위상 순서가 직렬 순서입니다.
2단계 잠금확장 뒤 축소. 충돌 직렬 가능을 보장하지만 교착이 생길 수 있습니다. 엄격한 2PL은 X 잠금을 커밋까지 쥡니다.
스냅샷 격리시작 시점 버전을 읽고 같은 항목 동시 쓰기는 한쪽을 중단합니다. 쓰기 비대칭은 막지 못합니다.
SSI읽기-쓰기 의존을 추적해 위험한 구조에서 한 거래를 중단합니다(PostgreSQL SERIALIZABLE).

한 줄 정리

직렬 가능성은 충돌 그래프의 순환 여부로 판정하며, 2PL은 실행 중에 순환을 막고 스냅샷 격리는 쓰기 비대칭을 남깁니다.
