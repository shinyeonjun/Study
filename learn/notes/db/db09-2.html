버퍼 고정, 교체, 수정 페이지 쓰기를 추적하기

두 칸뿐인 작업대에 세 번째 페이지를 놓아야 합니다. 다른 작업이 쓰고 있는 페이지는 옮기면 안 되고, 고친 페이지는 원래 저장소와 내용이 다를 수 있습니다. 이 두 조건을 교체 순서와 별도로 관리합니다.

이 장을 읽고 나면

  • 페이지·프레임·고정 횟수·수정 표시를 구별한다.
  • 상태별 읽기, 적중, 쓰기 비용을 시간 순서로 계산한다.
  • 핀과 교체의 불변식을 작은 메모리 모형으로 검사한다.

페이지 하나에 대응하는 프레임을 찾는다

저장소에 있는 페이지 A를 메모리 프레임에 올립니다. 버퍼 관리자의 페이지 테이블은 페이지 ID에서 현재 프레임으로 가는 대응입니다(보통 해시 표). 이름은 같지만 SY09의 운영체제 페이지 테이블(가상 페이지 → 물리 프레임)과는 다른 자료 구조입니다. 같은 페이지를 다시 달라고 하면 먼저 페이지 테이블을 확인합니다. 있으면 버퍼 적중, 없으면 빈 프레임을 쓰거나 다른 페이지를 내보내야 하는 실패입니다. 같은 페이지를 동시에 두 프레임에 올려 서로 다르게 수정하는 문제를 피하려면 메모리에서의 대응을 일관되게 관리해야 합니다.

페이지를 받은 동안에는 고정(pin) 횟수를 올립니다. 사용을 마칠 때는 내립니다. 0보다 큰 동안 해당 프레임을 다른 페이지로 덮을 수 없습니다. 고정 횟수가 0이면 현재 교체 후보가 될 수 있습니다. 수정 표시(dirty)는 버퍼에 있는 페이지의 변경을 저장소로 아직 옮기지 않았다는 뜻입니다. 사용 중인지, 쓰기 작업이 필요한지는 별개의 상태입니다.

고정되지 않은 후보 중에서 고른다

두 프레임에 A와 B가 있고 둘 다 사용 중이라면 C의 읽기를 바로 수행할 수 없습니다. 아래 단일 사용자 흐름은 이런 시도에 실패를 반환합니다. 다른 구현이 기다림을 제공한다면 계속 쓰고 있는 프레임을 안전하게 풀 수 있는 작업이 있는지 고려해야 합니다. 후보가 여럿이면 이 예에서는 마지막으로 요청(fetch)된 시각이 가장 오래된 페이지를 배출합니다(LRU). 실제 시스템은 비용이 적은 근사(시계 알고리즘, LRU-K 등)를 많이 씁니다. 이는 교체 정책입니다. 핀이 양수인 후보를 제외하는 것은 정책을 바꾸더라도 유지해야 하는 조건입니다.

순서요청누적 읽기누적 쓰기
1고정하면서 A 읽고 수정, B 읽음20
2둘이 고정된 채 C 요청20
3A 고정 해제, C 요청31
4C·B 고정 해제, B 다시 요청 후 해제31
5A 다시 읽음41

마지막 A 요청에서 B는 4단계에서 다시 요청됐으므로 더 오래전에 요청된 C를 배출합니다. C는 수정하지 않았으므로 추가 쓰기가 없습니다. A가 다시 읽힐 때 값이 7이면, A를 내보내기 전에 저장소에 수정 내용을 보냈다는 사실을 확인할 수 있습니다. 수정 페이지를 저장소에 쓰기 전에는 그 변경을 설명하는 로그가 먼저 영속돼야 한다는 규칙(WAL)이 있어, 실제 버퍼 관리자는 dirty 페이지를 쓰기 전에 로그를 그 페이지의 LSN까지 먼저 내보냅니다. 이 규칙과 실제 DB가 변경을 영구 기록했다고 선언하기 전에 필요한 로그와 저장 장치의 조건은 복구 단원에서 따로 다룹니다.

두 프레임의 메모리 모형으로 추적한다

disk = {"A": 0, "B": 0, "C": 0}
frames = {}
reads = writes = hits = tick = 0

def fetch(page):
    global reads, writes, hits, tick
    tick += 1
    if page in frames:
        hits += 1
    else:
        if len(frames) == 2:
            candidates = [p for p, f in frames.items() if f["pins"] == 0]
            if not candidates:
                return False
            victim = min(candidates, key=lambda p: frames[p]["last"])
            old = frames.pop(victim)
            if old["dirty"]:
                disk[victim] = old["value"]
                writes += 1
        frames[page] = {"value": disk[page], "pins": 0, "dirty": False}
        reads += 1
    frame = frames[page]
    frame["pins"] += 1
    frame["last"] = tick
    return True

def release(page):
    assert frames[page]["pins"] > 0
    frames[page]["pins"] -= 1

assert fetch("A")
frames["A"].update(value=7, dirty=True)
assert fetch("B")
assert not fetch("C")
print(sorted(frames), reads, writes)
release("A")
assert fetch("C")
assert "B" in frames and disk["A"] == 7
release("C")
release("B")
assert fetch("B")
release("B")
assert fetch("A")
print(sorted(frames), frames["A"]["value"])
print(reads, writes, hits)

실행 결과

['A', 'B'] 2 0
['A', 'B'] 7
4 1 1

예제는 실행이 한 번에 한 흐름에서 진행되고, 디스크 쓰기는 실패하지 않으며, 초기 페이지 ID가 알려져 있다고 둡니다. 모형에서 disk는 메모리 딕셔너리입니다. 실제 메모리 관리자에서 고정 횟수를 바꾸는 작업과 교체 후보를 고르는 작업이 동시에 실행된다면, 조회와 상태 갱신 사이에 다른 스레드가 끼어드는 경우도 생각해야 합니다.

한눈에 정리

핵심어기억할 기준
버퍼 적중·실패페이지 테이블에 있으면 적중(읽기 없음), 없으면 빈 프레임을 쓰거나 하나를 배출하고 읽습니다.
고정(pin)고정 횟수가 0보다 크면 배출할 수 없습니다. 교체 정책이 바뀌어도 지켜야 하는 조건입니다.
수정 표시(dirty)배출할 때 저장소에 써야 하는지를 정합니다. 고정 여부와는 별개입니다.
교체 정책고정되지 않은 후보 중에서 고릅니다. 예제는 LRU이며 실제로는 근사 정책도 씁니다.

한 줄 정리

고정 횟수는 "내보내도 되는가", 수정 표시는 "내보낼 때 써야 하는가", 교체 정책은 "누구를 내보낼까"를 정합니다.
