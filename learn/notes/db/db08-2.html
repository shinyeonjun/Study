DB08·2

메시지 큐와 재전달을 견디는 처리

주문 사건을 합계에 반영하고 완료 신호를 보내기 전에 작업자가 멈출 수 있습니다. 같은 메시지를 다시 받았을 때 금액이 두 배로 늘지 않도록 저장합니다.

이 장을 읽고 나면

  • 큐의 생산자·소비자와 완료 확인을 구별한다.
  • 시간 초과와 재전달이 중복을 만들 수 있는 이유를 설명한다.
  • 처리 식별자와 집계 변경을 같은 SQLite 트랜잭션에서 확인한다.

생산이 바로 처리로 이어질 필요는 없다

메시지 큐는 생산자가 보낸 작업이나 사건을 받아 소비자에게 전달하는 중간 단계입니다. 주문 서비스는 접수한 주문을 사건으로 보낼 수 있고, 집계 서비스가 나중에 처리할 수 있습니다. 생산과 처리가 다른 속도로 진행되므로 쌓인 메시지 수나 처리까지 기다린 시간을 측정할 수 있습니다.

네트워크 응답이 늦거나 시간이 초과됐을 때 요청한 쪽은 상대가 실제로 작업을 끝냈는지 모를 수 있습니다. 그래서 다시 요청하거나 큐가 메시지를 다시 보냅니다. 적어도 한 번 전달을 목표로 하는 큐에서도 같은 메시지가 여러 번 전달될 수 있습니다. 언제 어떤 조건에서 재전달하는지는 큐의 설정과 문서에 따릅니다.

완료 확인을 보내기 전후의 중단

소비자가 주문 사건 e101을 받아 집계에 10,000원을 더하고 커밋했습니다. 작업 완료 확인인 ACK를 보내기 전에 멈췄다면 큐는 처리했는지 모를 수 있습니다. 같은 사건이 다시 왔을 때 합계에 단순히 더하면 20,000원이 됩니다.

사건 식별자를 processed_events에 적고 금액을 함께 갱신합니다. 둘 다 같은 트랜잭션에 넣습니다. 변경만 남고 처리 기록이 없으면 중복 계산하고, 처리 기록만 남고 변경이 없으면 다시 받더라도 빠뜨릴 수 있기 때문입니다. 저장이 확정된 뒤에만 큐로 완료 확인을 보냅니다.

어느 사건이 같은지, 순서를 어떻게 볼지

이 예는 서로 다른 사건에 서로 다른 안정적인 event_id를 부여하고, 같은 ID로 다시 보내면 내용도 같다는 계약을 씁니다. 주문 하나에서 새 사건이 따로 생길 수 있으므로 주문 번호만으로 모든 메시지를 건너뛰면 정상 사건을 잃을 수 있습니다. 단일 합계로 더하는 순서는 결과를 바꾸지 않지만 상태 갱신은 오래된 사건이 나중에 오면 잘못된 상태가 될 수 있습니다. 그런 작업은 버전이나 순서 정책을 따릅니다.

한 DB에서 원자적으로 처리한 효과를 한 번 남겼더라도, 큐 자체가 메시지를 한 번만 배달했거나 다른 저장소·메일 등 외부 효과까지 한 번만 일어났음을 보장하지 않습니다. 재시도를 포함한 보장의 범위를 작업마다 확인합니다.

ACK 유실과 적용 실패를 모의로 확인

실행 예제

import sqlite3

db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE processed_events (event_id TEXT PRIMARY KEY NOT NULL);
    CREATE TABLE totals (slot INTEGER PRIMARY KEY CHECK (slot = 1),
                         total_won INTEGER NOT NULL);
    INSERT INTO totals VALUES (1, 0);
""")

def apply(event_id, amount, fail=False):
    with db:
        added = db.execute("""
            INSERT INTO processed_events (event_id) VALUES (?)
            ON CONFLICT(event_id) DO NOTHING
        """, (event_id,))
        if added.rowcount == 0:
            return "duplicate"
        db.execute("UPDATE totals SET total_won = total_won + ? WHERE slot = 1",
                   (amount,))
        if fail:
            raise ValueError("simulated interruption")
        return "applied"

def show():
    events = db.execute("SELECT COUNT(*) FROM processed_events").fetchone()[0]
    amount = db.execute("SELECT total_won FROM totals").fetchone()[0]
    print("events and amount:", events, amount)

print("e101:", apply("e101", 10000), "(ACK lost)")
print("e101 again:", apply("e101", 10000))
show()
try:
    apply("e102", 15000, fail=True)
except ValueError:
    print("e102: rolled back")
show()
print("e102 again:", apply("e102", 15000))
show()
db.close()

실행 결과

e101: applied (ACK lost)
e101 again: duplicate
events and amount: 1 10000
e102: rolled back
events and amount: 1 10000
e102 again: applied
events and amount: 2 25000

예제의 첫 재전달은 집계를 바꾸지 않습니다. 두 번째 사건은 합계 쓰기 뒤 모의 예외가 발생하지만 트랜잭션을 롤백하여 다음 시도에서 정상 처리됩니다. 실제 운영의 저장장치 장애와 큐는 여기서 만들지 않습니다.
