데이터베이스 · DB07 데이터 파이프라인

DB07·1

수집·검증·변환·적재와 수 대조

JSON을 가져오는 데 성공해도 모든 값이 주문 표에 맞는 것은 아닙니다. 여섯 기록을 검증한 뒤 적재된 네 건의 행 수와 금액을 다시 계산합니다.

이 장을 읽고 나면

  • 수집, 변환, 적재가 각각 하는 일을 구분한다.
  • 입도·키·필수값·범위를 검사하고 실패한 행을 구분한다.
  • 입력·제외·저장 행 수와 금액 집계를 대조한다.

여러 단계가 이어지는 과정

데이터 파이프라인은 여러 단계에 걸쳐 자료를 가져와 검증하고 변환한 뒤 쓰는 과정입니다. 수집 단계에는 목록의 여러 페이지와 수집 시각을 기록할 수 있습니다. 변환은 파이썬 객체를 목적에 맞는 열, 단위, 유형으로 바꾸는 일입니다. 적재는 안정적으로 분석할 수 있도록 결과를 데이터베이스 표에 저장하는 일입니다.

원본을 별도로 보존하면 어떤 변환이 결과를 바꿨는지 조사하기 쉽습니다. 보존은 자료의 이용 조건과 접근 권한, 가능한 저장 기간을 확인한 뒤 필요한 범위에서 합니다. 이번 예의 원본과 SQLite 표는 모두 메모리의 모의 자료입니다.

한 행이 올바른지 기준을 쓰기

적재할 clean_orders의 입도는 주문 한 건입니다. 식별자인 order_id는 양의 정수, status는 paid 또는 pending, total_won은 원 단위의 0 이상 정수여야 합니다. 한 배치에서 검증을 통과한 같은 번호가 두 번 오면 어떤 기록을 믿어야 하는지 판단할 수 없으므로 여기서는 배치를 중단합니다. 반복 전달과 정정의 규칙을 가진 경우는 다음 장에서 봅니다.

필요한 열이 빠지면 기본값을 넣기 전에 계약을 확인합니다. 예제의 true는 '사실이다'라는 불 값으로, 금액 1원을 의미하지 않습니다. Python에서 불 값은 정수의 하위 유형이라 type(amount) is int로 실제 정수만 허용합니다. 음수와 불 값을 담은 두 기록은 분석 표에 넣지 않고 위치와 사유만 따로 기록합니다.

통과 수와 열의 의미를 확인

원래 여섯 건 중 네 건이 통과하고 두 건이 제외되어 총합이 맞습니다. 상태별 합을 계산하면 완료 40,000원과 미결제 12,000원이 나옵니다. 결제 완료 주문의 할인 전 금액을 묻는 보고서에서는 완료 상태의 40,000원을 사용합니다. 이 예의 total_won은 할인 전 주문액이어서 실제 정산 금액을 알려면 추가 자료가 필요합니다.

왜 그럴까?

파이프라인이 오류 없이 끝났는데도 적재 행이 틀릴 수 있는 이유는?

모범 답 보기

모든 문자열이 정상적으로 해석돼도 일부 행을 잘못 제외하거나 키를 반복해 기록할 수 있습니다. 원본과 적재 결과의 행 대응, 값의 단위와 범위를 별도로 검증합니다.

로컬 JSON에서 SQLite 표 만들기

실행 예제

import json
import sqlite3

body = """[
    {"order_id":101,"status":"paid","total_won":10000},
    {"order_id":102,"status":"paid","total_won":15000},
    {"order_id":103,"status":"pending","total_won":12000},
    {"order_id":104,"status":"paid","total_won":15000},
    {"order_id":105,"status":"paid","total_won":-1},
    {"order_id":106,"status":"paid","total_won":true}
]"""
rows = json.loads(body)

def check(row):
    if not isinstance(row, dict):
        return "invalid order object"
    if type(row.get("order_id")) is not int or row["order_id"] <= 0:
        return "invalid order_id"
    if row.get("status") not in ("paid", "pending"):
        return "invalid status"
    if type(row.get("total_won")) is not int or row["total_won"] < 0:
        return "invalid total_won"
    return None

kept = []
rejected = []
seen_ids = set()
for position, row in enumerate(rows, start=1):
    reason = check(row)
    if reason:
        rejected.append((position, reason))
        continue
    order_id = row["order_id"]
    if order_id in seen_ids:
        raise ValueError("duplicate valid order_id in batch")
    seen_ids.add(order_id)
    kept.append((order_id, row["status"], row["total_won"]))

with sqlite3.connect(":memory:") as db:
    db.execute("""
        CREATE TABLE clean_orders (
            order_id INTEGER PRIMARY KEY,
            status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
            total_won INTEGER NOT NULL CHECK (total_won >= 0)
        )
    """)
    db.executemany("INSERT INTO clean_orders VALUES (?, ?, ?)", kept)
    saved = db.execute("SELECT COUNT(*) FROM clean_orders").fetchone()[0]
    summary = db.execute("""
        SELECT status, COUNT(*), SUM(total_won)
        FROM clean_orders GROUP BY status ORDER BY status
    """).fetchall()

db.close()
assert saved + len(rejected) == len(rows)
print("read, stored, rejected:", len(rows), saved, len(rejected))
print("rejected:", rejected)
print("summary:", summary)

실행 결과

read, stored, rejected: 6 4 2
rejected: [(5, 'invalid total_won'), (6, 'invalid total_won')]
summary: [('paid', 3, 40000), ('pending', 1, 12000)]

제외 목록은 모의 원본의 위치와 이유입니다. 자료 일부가 누락된 상태로 분석할 수 있는지는 목적과 사전 규칙에 따라 결정합니다. 일부 기록만 적재한 배치를 허용하지 않는 운영이라면 제외가 생긴 순간 분석 표에 변경을 확정하기 전에 멈출 수 있습니다.
