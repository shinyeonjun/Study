복합 인덱스의 접두 순서와 병목 찾기

고객 1의 결제 완료 주문을 날짜순으로 볼 때와 모든 고객의 결제 완료 주문을 볼 때는 찾을 키가 다릅니다. 같은 컬럼 이름이 들어 있어도 실행 계획이 달라질 수 있습니다.

이 장을 읽고 나면

  • 복합 키의 사전식 비교와 왼쪽 접두를 계산한다.
  • 정렬과 동점 처리까지 포함해 SQLite 실행 계획을 읽는다.
  • 데이터 행 수, 실행 시간, 반복 호출에서 가장 큰 비용을 찾아낸다.

복합 키를 왼쪽부터 비교

(customer_id, status, order_date) 세 열을 순서대로 가진 인덱스를 만듭니다. 고객 번호부터 비교하고 같은 고객 안에서 상태, 상태도 같을 때 날짜를 비교합니다. 원래 날짜순에 있던 103과 104는 이 키 순서에서 바뀝니다.

고객 번호와 상태를 함께 정하면 행이 같은 키 구간으로 이어집니다. 앞의 두 열은 인덱스 접두입니다. 그 안의 주문은 날짜순입니다. 상태만 알면 고객 1, 고객 2 등 다른 구간을 모두 고려해야 합니다. 고객 번호처럼 먼저 비교할 열이 주어지지 않으면 앞쪽 키를 건너뛰어 단번에 전체 상태를 찾기 어렵습니다. SQLite는 통계와 자료에 따라 앞쪽 값들을 반복하며 나머지 조건을 검색하는 skip-scan이나 인덱스 스캔을 고를 수 있습니다.

범위 조건과 뒤 열의 역할

일반적인 다중 열 인덱스에서 앞쪽 열의 등호 조건은 탐색 구간을 잘게 좁힙니다. 날짜 앞의 customer_id와 status가 모두 고정되어 있다면 날짜 범위로 이어서 좁힐 수 있습니다. 첫 조건부터 넓은 범위라면 그 뒤에 오는 열은 전체 범위 곳곳에 반복될 수 있어 한 번의 연속 구간을 더 좁히는 방식으로 쓰기 어렵습니다.

이 표의 인덱스에는 같은 인덱스 키끼리 행 ID 순으로 나오는 정보가 있습니다. 고객과 상태를 고정한 예제에서는 ORDER BY order_date, order_id도 만족합니다. 날짜 문자열은 앞 단원과 같은 고정 폭 YYYY-MM-DD입니다.

같은 표의 세 계획 비교

실행 예제

import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript("""
    CREATE TABLE customers (
        customer_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
    );
    CREATE TABLE orders (
        order_id INTEGER PRIMARY KEY,
        customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
        order_date TEXT NOT NULL,
        status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
        total_won INTEGER NOT NULL CHECK (total_won >= 0),
        coupon_won INTEGER CHECK (coupon_won >= 0)
    );
    """)
    db.executemany("INSERT INTO customers VALUES (?, ?)", [
        (1, 'Mina'),
        (2, 'Jun'),
        (3, 'Sol'),
    ])
    db.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)", [
        (101, 1, '2025-01-02', 'paid', 10000, None),
        (102, 1, '2025-01-03', 'paid', 15000, 1000),
        (103, 2, '2025-01-04', 'pending', 12000, None),
        (104, 2, '2025-01-05', 'paid', 15000, 0),
    ])

    db.execute("""
        CREATE INDEX idx_orders_customer_status_date
        ON orders(customer_id, status, order_date)
    """)
    queries = [
        ("prefix", """
            SELECT order_id, order_date FROM orders
            WHERE customer_id = ? AND status = ?
            ORDER BY order_date, order_id
        """, (1, "paid")),
        ("status alone", """
            SELECT order_id FROM orders WHERE status = ? ORDER BY order_id
        """, ("paid",)),
        ("sort by amount", """
            SELECT order_id FROM orders ORDER BY total_won, order_id
        """, ()),
    ]
    for label, query, values in queries:
        plan = [row[3] for row in db.execute("EXPLAIN QUERY PLAN " + query, values)]
        print(label, plan)
        print("  rows:", db.execute(query, values).fetchall())
db.close()

실행 결과

prefix ['SEARCH orders USING COVERING INDEX idx_orders_customer_status_date (customer_id=? AND status=?)']
  rows: [(101, '2025-01-02'), (102, '2025-01-03')]
status alone ['SCAN orders']
  rows: [(101,), (102,), (104,)]
sort by amount ['SCAN orders', 'USE TEMP B-TREE FOR ORDER BY']
  rows: [(101,), (103,), (102,), (104,)]

출력은 예제 자료와 SQLite 3.50.4의 선택입니다. 상태만 사용한 질의에 별도로 상태 인덱스를 두거나 자료와 통계를 바꾸면 선택은 달라질 수 있습니다. 실행 계획에는 측정한 소요 시간이 들어 있지 않습니다.

가장 오래 걸리는 일부터 찾기

예컨대 질의 한 번이 5ms이지만 주문 목록마다 100번 호출하면 순차적으로 SQL 호출에만 500ms가 듭니다. 다른 한 번의 정렬이 30ms라면 합계에서 먼저 볼 것은 반복 호출입니다. 반대로 한 번의 JOIN이 수십만 줄을 만들면 결합의 입도와 행 수를 확인합니다.

같은 자료 크기와 값 분포에서 계획, 반환 행 수, 반복 횟수와 실제 시간을 수집합니다. 캐시가 차 있는 실행과 비어 있는 실행은 구분합니다. 한 요소만 바꿔 전후의 결과와 시간을 대조하면 무엇이 빨라졌는지 설명할 수 있습니다. 네 행 예제는 실행 원리 실습이므로 시간의 우열을 판단하는 표본으로 쓰지 않습니다.
