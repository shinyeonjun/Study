멱등 적재와 재실행의 경계

같은 주문 페이지를 다시 받으면 주문 수가 두 배가 될까요? 주문 번호와 제공자 버전으로 같은 입력의 재처리와 실제 값의 정정을 구별합니다.

이 장을 읽고 나면

  • 같은 입력을 재실행해도 결과가 변하지 않는 멱등의 의미를 설명한다.
  • 올바른 키와 버전으로 중복, 정정, 오래된 기록을 구별한다.
  • 트랜잭션과 처리 위치 기록을 어떤 순서로 다루는지 설명한다.

중단 뒤 같은 자료가 도착한다

자료를 받은 뒤 DB에 저장하고, 저장 성공을 수집 기록에 남기기 전에 작업이 멈출 수 있습니다. 저장했더라도 다음 실행은 어디까지 끝났는지 몰라 방금 페이지를 다시 읽을 수 있습니다. 이미 적재한 기록을 한 줄씩 새로 추가하면 행 수와 금액이 틀어집니다.

같은 입력을 한 번 처리하거나 그 효과가 반영된 상태에서 여러 번 다시 적용해도 관찰할 결과가 같으면 멱등이라고 합니다. 최신 주문 표에서 관리할 대상은 주문 번호 하나당 한 행입니다. 다만 주문 번호만 비교해 모든 재등장을 무시하면 진짜 금액 정정을 놓칠 수 있습니다.

같은 키의 어떤 버전인지 보기

예제의 제공자는 한 주문에 대해 버전이 증가할수록 최신이라고 보장합니다. 첫 입력은 101번 버전 1, 10,000원입니다. 이 입력을 한 번 더 처리하면 같은 값이라 한 행 그대로입니다. 정정된 버전 2는 10,500원으로 바꿉니다. 뒤늦은 버전 1이 버전 2를 덮으면 최신 금액을 잃으므로 무시합니다.

동일한 최신 키와 버전에 서로 다른 값이 들어오면 계약 위반이므로 예제는 해당 배치를 중단합니다. 최신 상태만 보관하면 오래전에 대체된 버전의 모든 값은 검증할 수 없습니다. 과거 버전의 동일성도 검증해야 하면 별도로 버전 이력을 둡니다.

한 번의 쓰기와 수집 위치

UPSERT는 삽입할 때 고유 키와 충돌하면 정해 둔 규칙에 따라 갱신하거나 넘어갑니다. 다음 질의는 ON CONFLICT(order_id) DO UPDATE로 충돌 행을 찾고, 새 버전이 더 큰 경우에만 바꿉니다. excluded는 이번에 삽입하려던 값을 가리킵니다.

수집의 체크포인트는 방금 작업을 끝낸 위치를 기록해 다음 실행의 시작점을 정합니다. DB가 쓰기를 확정하기 전에 완료로 기록하면 중단 시 저장되지 않은 기록을 건너뛸 수 있습니다. 두 기록이 같은 DB에 있다면 같은 트랜잭션에 쓸 수 있습니다. 별도 시스템이면 재실행 시 중복 효과를 막고, 입력과 출력의 개수를 대조합니다.

재실행, 정정, 배치 실패를 인메모리로 확인

실행 예제

import sqlite3

db = sqlite3.connect(":memory:", autocommit=sqlite3.LEGACY_TRANSACTION_CONTROL)
db.execute("""
    CREATE TABLE latest_orders (
        order_id INTEGER PRIMARY KEY,
        source_version INTEGER NOT NULL CHECK (source_version > 0),
        total_won INTEGER NOT NULL CHECK (total_won >= 0)
    )
""")
upsert = """
    INSERT INTO latest_orders VALUES (?, ?, ?)
    ON CONFLICT(order_id) DO UPDATE SET
        source_version = excluded.source_version,
        total_won = excluded.total_won
    WHERE excluded.source_version > latest_orders.source_version
"""

def apply_batch(rows):
    with db:
        db.execute("BEGIN IMMEDIATE")
        for order_id, version, amount in rows:
            if not all(type(value) is int for value in (order_id, version, amount)):
                raise ValueError("order fields must be integers")
            if order_id <= 0 or version <= 0 or amount < 0:
                raise ValueError("invalid order fields")
            stored = db.execute("""
                SELECT source_version, total_won
                FROM latest_orders WHERE order_id = ?
            """, (order_id,)).fetchone()
            if stored is not None and stored[0] == version and stored[1] != amount:
                raise ValueError("inconsistent current version")
            db.execute(upsert, (order_id, version, amount))

def show(label):
    print(label, db.execute("SELECT * FROM latest_orders ORDER BY order_id").fetchall())

first = [(101, 1, 10000)]
apply_batch(first)
show("first:")
apply_batch(first)
show("retry:")
apply_batch([(101, 2, 10500)])
show("corrected:")
apply_batch(first)
show("old version:")
try:
    apply_batch([(102, 1, 15000), (101, 2, 9999)])
except ValueError as error:
    print("failed:", error)
show("after rollback:")
db.close()

실행 결과

first: [(101, 1, 10000)]
retry: [(101, 1, 10000)]
corrected: [(101, 2, 10500)]
old version: [(101, 2, 10500)]
failed: inconsistent current version
after rollback: [(101, 2, 10500)]

마지막 배치는 102번 삽입 뒤 101번의 최신 버전 충돌을 발견합니다. with db에서 예외가 빠져나갈 때 트랜잭션을 롤백해 102번도 보이지 않습니다. 이 예제는 Python 3.12 이상에서 트랜잭션 제어 방식을 명시하고, 첫 조회 전 BEGIN IMMEDIATE로 쓰기 트랜잭션을 시작합니다. 앞 장과 같이 양의 정수 주문 번호와 버전, 0 이상의 정수 금액만 받아들입니다. 여러 연결이 동시에 쓰려는 환경에서는 잠금 대기와 실패의 처리도 설계합니다.
