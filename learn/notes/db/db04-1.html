DB04·1

저장할 값과 관계에 제약조건 두기

주문에 고객이 꼭 필요할 수도 있고, 쿠폰액은 나중에 확인될 수도 있습니다. 두 경우의 규칙을 데이터베이스에 직접 적어 어디에서 값이 들어와도 같은 기준으로 검사합니다.

이 장을 읽고 나면

  • 기본 키, 외래 키, NOT NULL, UNIQUE, CHECK가 검사하는 대상을 구별한다.
  • NULL을 허용하는 비교 제약의 의미를 설명한다.
  • 여러 종류의 잘못된 새 기록을 입력해 어떤 제약이 거부하는지 확인한다.

업무의 규칙을 스키마에 적기

문구점에서 주문은 주문 번호 한 건당 한 행이고, 이미 등록된 고객에게 속합니다. 제약조건은 표가 받아들일 값을 제한하는 스키마의 일부입니다. 사람이 직접 입력하거나 가져오기 스크립트가 기록해도 데이터베이스에서 같은 규칙을 적용합니다.

예제에서는 고객 표시 이름은 같을 수 있고, 고객의 외부 계정 코드는 같으면 안 됩니다. UNIQUE를 외부 코드에 두고, 주 식별자인 customer_id는 기본 키로 유지합니다. 외래 키는 참조 존재를 검사하지만 참조 열이 선택 사항이면 NULL을 허용할 수 있습니다. 모든 주문에 반드시 고객이 있다면 외래 키에 NOT NULL도 같이 둡니다.

외래 키에는 참조되는 행이 지워지거나 그 키가 바뀔 때의 동작(참조 동작)도 정할 수 있습니다. 아무것도 적지 않으면 NO ACTION이며, 주문이 남아 있는 고객을 지우려 하면 이 장의 예제 표에서 FOREIGN KEY constraint failed 오류로 거부됩니다.

ON DELETE 동작고객 1을 지울 때 주문 101·102는
NO ACTION · RESTRICT참조가 남아 있으면 삭제를 거부한다(기본값은 NO ACTION).
CASCADE주문도 함께 지운다.
SET NULL주문의 customer_id를 NULL로 바꾼다. 그 열이 NOT NULL이면 실패한다.

NO ACTION과 RESTRICT는 검사 시점만 다릅니다(RESTRICT는 즉시, NO ACTION은 문장 끝이나 지연 설정 시 커밋 때). 주문처럼 남겨야 하는 거래 기록에 CASCADE를 걸면 고객 하나를 지울 때 이력까지 사라지므로 신중히 고릅니다.

0보다 작은 값과 값 없음

SQLite와 PostgreSQL에서 CHECK (coupon_won >= 0)의 결과가 거짓이면 행을 거부합니다. 쿠폰값이 NULL이면 결과가 미지이므로 이 제약을 통과합니다. '쿠폰을 쓰지 않음이 확인되어 0원'과 '쿠폰 기록을 확인할 수 없음'을 구별하려고 여기서는 NULL을 허용합니다. 필수 금액인 total_won에는 비음수 조건과 NOT NULL을 둘 다 둡니다.

SQLite 일반 테이블의 INTEGER 같은 선언은 유형 선택에 영향을 주지만 모든 입력 유형을 엄격히 막는 선언은 아닙니다. 예를 들어 값이 텍스트로 저장되면 0 이상을 비교하는 CHECK만으로 정수 입력임을 보장하기 어렵습니다. 엄격한 저장 유형이 필요하면 STRICT 테이블 등 별도의 유형 제약을 검토합니다. 날짜 문자열이 실제 달력 날짜인지, 주문액이 항목 합과 맞는지처럼 열 정의나 이번 CHECK 하나로 확인되지 않는 규칙은 별도의 검사와 쓰기 절차가 필요합니다. 일반 테이블의 일부 기본 키 선언에서 SQLite가 NULL을 허용하는 역사적 동작이 있으므로 이 교재의 복합 키 각 열에는 NOT NULL을 명시했습니다.

학습용 인메모리 표에서 거부 조건 확인

읽기와 쓰기가 구분되도록 여기서는 이미 있는 기록을 저장한 다음 입력을 한 문장씩 실행합니다. sqlite3.IntegrityError는 제약 검사가 입력을 거부했음을 알려줍니다. 서로 다른 종류의 오류를 구별하려고 각 입력마다 하나의 규칙만 어기도록 값을 정했습니다.

실행 예제

import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript("""
    CREATE TABLE customers (
        customer_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
    );
    CREATE TABLE orders (
        order_id INTEGER PRIMARY KEY,
        customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
        order_date TEXT NOT NULL,
        status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
        total_won INTEGER NOT NULL CHECK (total_won >= 0),
        coupon_won INTEGER CHECK (coupon_won >= 0)
    );
    """)
    db.executemany("INSERT INTO customers VALUES (?, ?)", [
        (1, 'Mina'),
        (2, 'Jun'),
        (3, 'Sol'),
    ])
    db.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)", [
        (101, 1, '2025-01-02', 'paid', 10000, None),
        (102, 1, '2025-01-03', 'paid', 15000, 1000),
        (103, 2, '2025-01-04', 'pending', 12000, None),
        (104, 2, '2025-01-05', 'paid', 15000, 0),
    ])

    def attempt(label, sql, params):
        try:
            db.execute(sql, params)
        except sqlite3.IntegrityError:
            print(label, "rejected")
        else:
            print(label, "accepted")

    db.execute("""
        CREATE TABLE customer_codes (
            customer_id INTEGER PRIMARY KEY REFERENCES customers(customer_id),
            external_code TEXT NOT NULL UNIQUE
        )
    """)
    db.execute("INSERT INTO customer_codes VALUES (?, ?)", (1, "REF-A"))
    attempt("duplicate primary key",
            "INSERT INTO customers VALUES (?, ?)", (1, "New name"))
    attempt("name missing",
            "INSERT INTO customers VALUES (?, ?)", (4, None))
    attempt("duplicate external code",
            "INSERT INTO customer_codes VALUES (?, ?)", (2, "REF-A"))
    order_sql = "INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)"
    attempt("unknown customer", order_sql, (105, 99, "2025-01-06", "paid", 2000, 0))
    attempt("negative coupon", order_sql, (106, 1, "2025-01-06", "paid", 2000, -1))
    attempt("coupon not recorded", order_sql, (107, 1, "2025-01-06", "paid", 2000, None))
    print("accepted orders:", db.execute("SELECT COUNT(*) FROM orders").fetchone()[0])
db.close()

실행 결과

duplicate primary key rejected
name missing rejected
duplicate external code rejected
unknown customer rejected
negative coupon rejected
coupon not recorded accepted
accepted orders: 5

SQLite에서 외래 키 검사를 켜는 PRAGMA는 연결마다 적용합니다. 이 예는 첫 쓰기 전에 켭니다. 기본 설정에 의존하지 않고 켜졌음을 확인하려면 PRAGMA foreign_keys 결과가 1인지도 검사할 수 있습니다.

왜 그럴까?

앱 화면에도 필수값 검사가 있는데 DB에서도 NOT NULL이 필요한 이유는?

모범 답 보기

자료가 그 화면을 거치지 않고 가져오기나 다른 프로그램에서 올 수 있습니다. 화면은 바로 오류를 알려 줄 수 있고 DB는 저장 경로 전반에 규칙을 적용합니다.
