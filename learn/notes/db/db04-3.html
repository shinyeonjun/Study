DB04·3

트랜잭션과 ACID로 변경을 함께 확정하기

주문 103의 상태를 결제 완료로 바꾸고, 그 주문에 든 공책 두 개를 재고에서 뺍니다. 재고가 부족하면 주문 상태가 이미 바뀌었더라도 두 작업을 모두 되돌립니다.

이 장을 읽고 나면

  • BEGIN, COMMIT, ROLLBACK의 경계를 정한다.
  • 트랜잭션의 원자성·일관성·격리성·지속성을 구별한다.
  • 더티 읽기·반복 불가능한 읽기·팬텀 읽기와 네 격리 수준을 짝짓는다.
  • 실패한 쓰기와 같은 요청의 재시도 뒤에도 데이터가 일관적인지 확인한다.

서로 떨어진 두 쓰기를 하나의 작업으로

여러 SQL 문을 묶어 하나의 작업 단위로 처리하는 것을 트랜잭션이라 합니다. 결제 완료 상태인데 그 주문에 필요한 재고가 줄지 않으면 두 표가 서로 맞지 않습니다. 예에서는 이전에 배운 주문 자료의 orders와 order_items에 inventory를 추가합니다. 결제 완료는 이 연습 안의 주문 상태입니다.

BEGIN으로 시작하고 모든 작업이 맞으면 COMMIT으로 확정합니다. 중간 검사나 쓰기가 실패하면 ROLLBACK으로 이 트랜잭션에 포함된 변경을 되돌립니다. SQL 한 문장마다 확정해 버렸다면 두 번째 쓰기가 실패해도 먼저 확정한 상태 변경은 되돌릴 수 없습니다.

ACID에서 네 가지를 따로 확인

원자성은 이 트랜잭션에서 정한 변경이 전부 적용되거나 전부 취소된다는 성질입니다. 일관성은 시작이 유효하고 쓰기 절차가 올바르면 확정 후에도 제약과 업무 규칙을 만족한다는 의미입니다. 예제의 CHECK (qty >= 0)는 음수 재고를 거부합니다. 주문마다 공책과 펜을 정확히 어떤 수만큼 빼야 하는지는 코드가 주문항목을 읽어 정합니다.

격리성은 여러 트랜잭션이 겹칠 때 변경이 언제 보이고 어떻게 함께 실행될지에 관한 성질입니다. 일반적인 SQLite 연결에서는 커밋하기 전 다른 연결에 진행 중인 변경을 보여주지 않으며, 같은 데이터베이스에는 동시에 한 쓰기 트랜잭션만 진행할 수 있습니다. 파일 저장 방식과 DBMS마다 읽기 규칙과 잠금 동작은 다를 수 있습니다.

지속성은 파일형 DB에서 커밋을 성공했다고 알린 뒤에도 그 변경이 장애로 사라지지 않는 성질입니다. 실제 보장은 저장 장치와 동기화 설정의 조건을 따릅니다. 메모리 DB는 연결이 끝나면 사라져 이번 실습에서는 저장 장치에 관한 지속성을 시험하지 않습니다.

격리 수준과 동시 실행 이상 외우기

여러 트랜잭션을 정말 하나씩 차례로 실행한 것과 같은 결과를 보장하는 것을 직렬화 가능(serializable)이라고 합니다. 가장 안전하지만 기다림이 늘 수 있어서, SQL 표준은 더 약한 격리 수준을 정하고 각 수준에서 생길 수 있는 이상 현상을 정의합니다. 재고 1개인 상품 11을 두 트랜잭션 T1, T2가 다룬다고 합시다.

  • 더티 읽기(dirty read): T2가 재고를 0으로 바꿨지만 아직 커밋하지 않았는데 T1이 그 0을 읽습니다. 뒤에 T2가 롤백하면 T1은 존재한 적 없는 값을 근거로 판단한 셈입니다.
  • 반복 불가능한 읽기(non-repeatable read): T1이 재고 1을 읽은 뒤 T2가 0으로 바꾸고 커밋합니다. T1이 같은 행을 다시 읽으면 0이 나옵니다.
  • 팬텀 읽기(phantom read): T1이 WHERE status = 'pending'으로 주문을 두 번 세는 사이 T2가 pending 주문을 새로 넣고 커밋합니다. 두 번째 조회에 없던 행이 나타납니다. 행의 값이 아니라 조건에 맞는 행의 집합이 바뀝니다.

표준은 각 수준에서 '일어나면 안 되는 현상'만 정하므로 실제 제품은 더 강하게 구현할 수 있습니다. 기본 수준은 PostgreSQL이 READ COMMITTED, MySQL(InnoDB)이 REPEATABLE READ입니다. PostgreSQL의 REPEATABLE READ는 트랜잭션 시작 시점의 스냅숏을 읽게 해서 팬텀도 생기지 않지만, 두 트랜잭션이 서로 다른 행을 읽고 써서 함께 지켜야 할 규칙을 깨는 경우는 SERIALIZABLE에서만 막습니다. SQLite는 쓰기 트랜잭션을 한 번에 하나만 허용하므로 기본적으로 직렬화 가능하게 동작합니다. 정확한 동작은 각 DBMS 문서를 확인합니다.

두 트랜잭션이 같은 값을 읽고 각자 계산해 덮어써서 한쪽 변경이 사라지는 현상은 갱신 손실(lost update)이라고 합니다. 표준 표에는 없지만 READ COMMITTED에서 '읽고 계산해서 덮어쓰기'를 하면 생길 수 있습니다. 막는 방법은 아래 예제처럼 UPDATE … SET qty = qty - ? WHERE qty >= ? 한 문장 안에서 조건 검사와 차감을 함께 하거나, PostgreSQL·MySQL의 SELECT … FOR UPDATE로 읽을 때 행을 잠그는 것입니다(SQLite에는 FOR UPDATE가 없습니다).

안전하게 차감하고 성공 여부를 검사

아래의 BEGIN IMMEDIATE는 SQLite의 쓰기 트랜잭션을 즉시 시작합니다. 다른 연결이 이미 쓰는 중이라면 잠금 대기나 SQLITE_BUSY가 생길 수 있습니다. 이 예제는 Python 3.12 이상에서 sqlite3의 트랜잭션 제어 방식을 명시합니다. 주문 상태는 pending인 경우에만 바꾸고, 재고는 필요한 수량 이상인 경우에만 뺍니다. rowcount로 갱신 건수가 1인지 확인합니다. 0이면 이미 처리된 주문, 잘못된 번호, 또는 수량 조건을 충족하지 못한 경우가 있어 이 예에서는 작업을 취소하고 이유를 돌려줍니다.

실행 예제

import sqlite3

with sqlite3.connect(":memory:", autocommit=sqlite3.LEGACY_TRANSACTION_CONTROL) as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript("""
    CREATE TABLE customers (
        customer_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
    );
    CREATE TABLE orders (
        order_id INTEGER PRIMARY KEY,
        customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
        order_date TEXT NOT NULL,
        status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
        total_won INTEGER NOT NULL CHECK (total_won >= 0),
        coupon_won INTEGER CHECK (coupon_won >= 0)
    );
    CREATE TABLE products (
        product_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        list_price_won INTEGER NOT NULL CHECK (list_price_won >= 0)
    );
    CREATE TABLE order_items (
        order_id INTEGER NOT NULL REFERENCES orders(order_id),
        line_no INTEGER NOT NULL,
        product_id INTEGER NOT NULL REFERENCES products(product_id),
        qty INTEGER NOT NULL CHECK (qty > 0),
        unit_price_won INTEGER NOT NULL CHECK (unit_price_won >= 0),
        PRIMARY KEY (order_id, line_no)
    );
    """)
    db.executemany("INSERT INTO customers VALUES (?, ?)", [
        (1, 'Mina'),
        (2, 'Jun'),
        (3, 'Sol'),
    ])
    db.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)", [
        (101, 1, '2025-01-02', 'paid', 10000, None),
        (102, 1, '2025-01-03', 'paid', 15000, 1000),
        (103, 2, '2025-01-04', 'pending', 12000, None),
        (104, 2, '2025-01-05', 'paid', 15000, 0),
    ])
    db.executemany("INSERT INTO products VALUES (?, ?, ?)", [
        (11, 'notebook', 6000),
        (12, 'pen', 2000),
        (13, 'pouch', 3000),
    ])
    db.executemany("INSERT INTO order_items VALUES (?, ?, ?, ?, ?)", [
        (101, 1, 11, 1, 6000),
        (101, 2, 12, 2, 2000),
        (102, 1, 11, 2, 6000),
        (102, 2, 13, 1, 3000),
        (103, 1, 11, 2, 6000),
        (104, 1, 13, 5, 3000),
    ])

    db.execute("""
        CREATE TABLE inventory (
            product_id INTEGER PRIMARY KEY REFERENCES products(product_id),
            qty INTEGER NOT NULL CHECK (qty >= 0)
        )
    """)
    db.execute("INSERT INTO inventory VALUES (?, ?)", (11, 1))
    db.commit()

    def reserve_order(order_id):
        db.execute("BEGIN IMMEDIATE")
        try:
            change = db.execute("""
                UPDATE orders SET status = 'paid'
                WHERE order_id = ? AND status = 'pending'
            """, (order_id,))
            if change.rowcount != 1:
                raise ValueError("order not pending")
            items = db.execute("""
                SELECT product_id, SUM(qty)
                FROM order_items WHERE order_id = ?
                GROUP BY product_id ORDER BY product_id
            """, (order_id,)).fetchall()
            if not items:
                raise ValueError("no order items")
            for product_id, needed in items:
                change = db.execute("""
                    UPDATE inventory SET qty = qty - ?
                    WHERE product_id = ? AND qty >= ?
                """, (needed, product_id, needed))
                if change.rowcount != 1:
                    raise ValueError("insufficient stock")
            db.commit()
        except Exception:
            db.rollback()
            raise

    def show_order_103():
        status = db.execute(
            "SELECT status FROM orders WHERE order_id = ?", (103,)
        ).fetchone()[0]
        stock = db.execute(
            "SELECT qty FROM inventory WHERE product_id = ?", (11,)
        ).fetchone()[0]
        print(status, "stock:", stock)

    def try_order_103():
        try:
            reserve_order(103)
        except ValueError as error:
            print("rejected:", error)
        else:
            print("committed")
        show_order_103()

    try_order_103()
    db.execute("UPDATE inventory SET qty = qty + ? WHERE product_id = ?", (4, 11))
    db.commit()
    try_order_103()
    try_order_103()
db.close()

pending stock: 1
committed
paid stock: 3
rejected: order not pending
paid stock: 3

첫 시도는 주문 상태를 바꾼 뒤 재고가 모자라 rollback()에 이릅니다. 별도 재입고 뒤의 시도는 공책 두 개를 차감하고 commit()합니다. 세 번째 시도에서는 주문이 이미 처리돼 재고를 다시 줄이지 않습니다. 다른 연결이 쓰는 중이면 SQLite에서 시작이나 쓰기 시점에 잠금 대기 또는 실패가 생길 수 있으므로 실제 애플리케이션은 오류를 받아 처리 단위 전체를 얼마나 다시 시도할지 정합니다.

왜 그럴까?

재고가 한 개뿐인 두 요청이 먼저 재고 수를 읽고 각자 저장하면 어떤 문제가 생길까?

모범 답 보기

두 요청이 모두 같은 첫 재고량을 기준으로 판단하면 둘 다 확보했다고 판단할 수 있습니다. 예제는 읽은 값으로 덮어쓰는 대신 갱신 문장에 수량 조건을 걸고 갱신된 행 수까지 확인합니다. 주문과 재고에 관한 변경을 한 트랜잭션에 묶습니다.
