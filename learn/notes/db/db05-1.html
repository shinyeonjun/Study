DB05·1

인덱스에서 찾고 실행 계획으로 확인하기

네 주문 중 금액이 15,000원 이상인 두 주문을 찾습니다. 처음부터 모든 주문을 검사하는 방법과, 금액순으로 만든 인덱스에서 읽기 시작하는 방법을 비교합니다.

이 장을 읽고 나면

  • 표 스캔과 인덱스의 시작 위치 검색을 구별한다.
  • B-tree 페이지의 키 구간이 탐색을 줄이는 원리를 설명한다.
  • SQLite에서 같은 결과를 두 방법으로 읽고 실행 계획을 확인한다.

표의 행을 하나씩 보면서 찾기

주문 네 건의 총액이 차례로 10,000, 15,000, 12,000, 15,000원입니다. WHERE total_won >= 15000 조건을 확인하려면 주문을 차례로 읽어 각 금액을 비교할 수 있습니다. 전체 표에서 읽어야 할 후보를 줄일 구조가 없을 때 이런 스캔을 사용할 수 있습니다. 이번에는 금액순 표시도 요구하므로 선택한 결과를 정렬해야 할 수 있습니다.

인덱스는 같은 자료에 대한 별도의 접근 구조입니다. 금액을 정렬 기준으로 삼은 인덱스에는 같은 금액을 가진 여러 주문이 각자 들어갈 수 있습니다. SQLite 행 ID가 있는 이 주문 표에서는 보조 인덱스가 그 행 ID도 가지고 있으므로 금액 값에서 원본 주문과 연결됩니다.

여러 키를 담는 페이지에서 읽을 범위를 고르기

B-tree 계열의 구조는 키를 작은 구간으로 나누어 저장합니다. 디스크의 자료를 읽는 단위 중 하나인 페이지에 여러 키나 자식 페이지를 찾을 정보가 들어갑니다. 맨 위에서 키 범위를 확인하고 필요한 하위 페이지로 내려갑니다. 목표 금액을 처음 찾은 뒤에는 키 순서대로 필요한 범위를 읽을 수 있습니다.

한 페이지에 자식 페이지를 가리키는 항목이 많이 들어가므로 트리는 넓고 낮습니다. 한 노드가 가리킬 수 있는 자식 수를 팬아웃(fan-out) f라 하면, 높이 h인 트리는 맨 아래에서 최대 약 fh개 구간을 구분합니다. f=100이면 높이 3으로 1003=1,000,000개, 높이 4로 1억 개를 구분하므로 키 하나를 찾을 때 읽는 페이지 수는 약 logf N으로 아주 느리게 늘어납니다. 자식이 2개인 이진 탐색 트리라면 백만 개에 약 20단계(log2 1,000,000 ≈ 19.9)가 필요합니다. B-tree는 삽입·삭제 때 노드를 나누거나 합쳐 모든 잎의 깊이를 같게 유지하므로 이 높이가 한쪽으로 치우치지 않습니다.

많은 DBMS가 쓰는 변형인 B+tree는 모든 키 항목을 잎에 두고 위쪽 노드에는 길 안내용 키만 두며, 잎끼리 순서대로 이어 둡니다. 범위 검색은 첫 잎을 찾은 뒤 옆 잎으로 차례로 넘어가며 읽습니다. 반면 해시 인덱스는 키를 해시값으로 바로 찾으므로 등호 검색에는 빠르지만 >= 같은 범위나 정렬에는 쓰지 못합니다.

가령 원본에 10,000개 페이지가 있고 인덱스 루트부터 필요한 키의 첫 잎까지 페이지 3개를 읽는다고 합시다. 전체 표를 훑는 것과 트리의 3개 페이지에서 시작점을 찾는 것은 읽어야 할 후보 수가 다릅니다. 뒤에 수천 건이 일치하면 결과를 모두 읽고 돌려주는 비용도 듭니다. 인덱스만으로 SELECT 열을 구할 수 없을 때는 짝이 맞는 원본 행도 읽습니다.

실행 계획에 나온 SCAN과 SEARCH

EXPLAIN QUERY PLAN은 SQLite가 어떤 방식으로 자료에 접근할지 설명합니다. SCAN은 해당 접근에서 넓게 훑는다는 표시이고 인덱스 순서대로 전체를 읽는 경우에도 나올 수 있습니다. SEARCH는 조건으로 일부 범위나 키를 찾는 접근입니다. USING COVERING INDEX는 이 질의가 인덱스의 값만 읽고 필요한 열을 전부 채울 수 있다는 뜻입니다. USE TEMP B-TREE FOR ORDER BY는 결과를 정렬하기 위한 별도 구조의 일입니다.

실행 계획의 요약 문구는 SQLite 버전에 따라 달라질 수 있습니다. 아래에서는 3.50.4에서 확인한 출력을 보입니다. SQL의 >=가 결과 기준이며, 계획의 total_won>? 표시는 해당 범위를 찾았다는 요약입니다.

실행 예제

import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript("""
    CREATE TABLE customers (
        customer_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
    );
    CREATE TABLE orders (
        order_id INTEGER PRIMARY KEY,
        customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
        order_date TEXT NOT NULL,
        status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
        total_won INTEGER NOT NULL CHECK (total_won >= 0),
        coupon_won INTEGER CHECK (coupon_won >= 0)
    );
    """)
    db.executemany("INSERT INTO customers VALUES (?, ?)", [
        (1, 'Mina'),
        (2, 'Jun'),
        (3, 'Sol'),
    ])
    db.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)", [
        (101, 1, '2025-01-02', 'paid', 10000, None),
        (102, 1, '2025-01-03', 'paid', 15000, 1000),
        (103, 2, '2025-01-04', 'pending', 12000, None),
        (104, 2, '2025-01-05', 'paid', 15000, 0),
    ])

    query = """
        SELECT order_id, total_won FROM orders
        WHERE total_won >= ?
        ORDER BY total_won, order_id
    """
    values = (15_000,)

    def show(label):
        plan = db.execute("EXPLAIN QUERY PLAN " + query, values).fetchall()
        print(label, [row[3] for row in plan])
        print("  rows:", db.execute(query, values).fetchall())

    show("before")
    db.execute("CREATE INDEX idx_orders_total ON orders(total_won)")
    show("after")
db.close()

실행 결과

before ['SCAN orders', 'USE TEMP B-TREE FOR ORDER BY']
  rows: [(102, 15000), (104, 15000)]
after ['SEARCH orders USING COVERING INDEX idx_orders_total (total_won>?)']
  rows: [(102, 15000), (104, 15000)]

인덱스를 만든 뒤 정렬 단계가 사라진 이유는 인덱스 항목이 이미 total_won 순서이고, 같은 금액끼리는 행 ID 순서로 놓여 있기 때문입니다. order_id는 INTEGER PRIMARY KEY라 행 ID와 같은 값이므로 인덱스를 앞에서부터 읽기만 해도 ORDER BY total_won, order_id가 만족됩니다. 같은 이유로 SELECT의 두 열이 모두 인덱스 항목 안에 있어 원본 행을 읽지 않는 COVERING INDEX가 됩니다.

저장과 갱신에도 비용이 생긴다

인덱스를 추가하면 별도 공간이 필요합니다. 주문 추가, 삭제, 인덱스 열 변경 때 필요한 인덱스도 갱신합니다. 검색이 잦은 조건이 있는지, 검색으로 읽을 행이 얼마나 줄어드는지, 쓰기는 얼마나 자주 일어나는지 같이 봅니다. 작은 표나 대부분의 행을 돌려주는 질의에는 스캔이 유리할 수 있습니다.
