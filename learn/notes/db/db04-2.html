DB04·2

함수 종속과 갱신 이상을 줄이는 정규화

주문 항목 옆에 고객 이름과 상품명을 직접 넣으면 읽기 쉬워 보입니다. 같은 이름의 사본을 여러 번 갱신해야 할 때 어떤 문제가 생기는지 살펴보고, 사실의 단위대로 나눕니다.

이 장을 읽고 나면

  • 업무의 함수 종속을 열의 실제 값과 구별한다.
  • 삽입·갱신·삭제 이상을 설명하고 1~3정규형과 BCNF의 조건을 구별한다.
  • 현재 가격과 주문 당시 단가를 각각 적절한 표에 보존한다.

같은 사실을 여러 곳에 기록하면

손으로 보기 좋은 보고서에는 고객 이름과 상품 이름이 각 항목 줄에 나올 수 있습니다. 하지만 고객과 상품의 현재 표시 이름을 이런 항목 줄만으로 관리하면 같은 사실이 여러 곳에 반복됩니다. 고객 1의 이름은 주문 101과 102의 네 줄에 나타납니다.

고객 이름의 네 사본 중 하나만 바꾸면 어느 값이 최신인지 애매해지는 갱신 이상이 생깁니다. 주문 항목이 있어야 고객을 추가할 수 있으면 삽입 이상이고, 마지막 주문 항목을 지울 때 고객 정보도 사라지면 삭제 이상입니다. 별개의 사실을 한 행의 생애에 같이 묶었기 때문에 생기는 문제입니다.

어느 값이 무엇을 결정하는가?

함수 종속 X → Y는 업무상 올바른 모든 자료에서 X가 같은 두 행의 Y도 같아야 한다는 규칙입니다. 하나의 고객 번호에 현재 이름을 하나만 둔다면 customer_id → customer_name입니다. 이름이 같을 수 있으므로 반대 방향은 자동으로 성립하지 않습니다. 오늘의 자료에서 우연히 한 사람씩 나왔다는 것과 업무에서 항상 성립해야 한다는 것을 구별합니다.

하나로 합친 항목 표의 유일한 후보 키를 (order_id,line_no)라 둡니다. 주문이 같으면 고객 번호와 주문일도 같아서 order_id → customer_id, order_date입니다. 항목별 수량은 같은 주문에서도 다를 수 있어 주문 번호와 항목 번호 모두 필요합니다. 상품 번호는 현재 이름과 정가를 정하지만, 할인·가격 변경이 있다면 과거 거래 단가까지 결정하지 않습니다.

세 단계가 확인하는 규칙

정규화는 이런 종속에 따라 표를 다듬어 같은 사실의 반복과 갱신 이상을 줄입니다. 1정규형은 모든 속성의 값이 더 나누어 다루지 않는 하나의 값, 곧 원자값인 상태입니다. 예를 들어 주문 한 셀에 상품 번호 여러 개를 쉼표로 합치거나 product1, product2, product3처럼 반복 열을 두는 대신, 주문항목에 상품 한 줄을 따로 둡니다.

2정규형은 1정규형이면서, 어떤 후보 키에도 들어 있지 않은 비키 속성이 후보 키 전체가 아니라 그 진부분집합에 함수 종속되지 않는 상태입니다. 키의 일부에만 종속되는 것을 부분 함수 종속이라고 합니다. 예시에서 고객 번호와 주문일은 복합 키 (order_id,line_no) 중 order_id만으로 정해지는 부분 종속이므로 주문 표로 옮깁니다. 모든 후보 키가 열 하나로 된 표는 키의 진부분집합이 공집합뿐이라 1정규형이면 자동으로 2정규형입니다.

3정규형은 2정규형이면서, 비키 속성이 키가 아닌 다른 속성을 거쳐 키에 종속되는 이행 함수 종속이 없는 상태입니다. 주문 표에 customer_id와 customer_name을 함께 두면 order_id → customer_id → customer_name입니다. 고객은 여러 번 주문할 수 있으므로 customer_id는 주문 표의 키가 아닌데도 customer_name을 결정합니다. 그래서 고객 1의 이름이 주문 101과 102 두 행에 반복되고, 이것이 3정규형 위반의 증상입니다. 현재 고객 이름은 고객 표로 옮겨 거기서 읽고, 상품 이름도 같은 이유로 상품 표에 둡니다.

정확한 일반 기준은 이렇습니다. 비자명한 함수 종속 X → A 각각에 대해 X가 슈퍼키(행을 유일하게 식별하는 열 집합)이거나 A가 어떤 후보 키에 포함된 속성이면 3정규형입니다. A가 X에 이미 포함된 종속, 예를 들어 (order_id, line_no) → order_id는 자명한 종속이라 따지지 않습니다.

BCNF: 결정하는 쪽은 모두 슈퍼키

BCNF(보이스-코드 정규형)는 3정규형의 예외인 'A가 후보 키에 포함된 속성이면 괜찮다'를 없앤 기준입니다. 모든 비자명한 함수 종속 X → A에서 X가 슈퍼키여야 합니다. 대부분의 표에서는 3정규형이면 BCNF이고, 후보 키가 여러 개이며 서로 겹칠 때 차이가 납니다.

풀이 예제 · 3정규형이지만 BCNF가 아닌 표

수강(학생, 과목, 강사) 표에서 업무 규칙이 ① 한 학생은 한 과목을 한 강사에게만 듣고 ② 강사 한 명은 한 과목만 가르친다고 합시다. 함수 종속은 (학생, 과목) → 강사와 강사 → 과목입니다.

① 후보 키 찾기: (학생, 과목)은 강사를 결정하므로 모든 열을 정합니다. (학생, 강사)도 강사 → 과목으로 과목을 얻으므로 모든 열을 정합니다. 학생·과목·강사 하나만으로는 나머지를 모두 정하지 못하므로 두 조합 모두 후보 키입니다.
② 비키 속성: 세 열이 모두 어떤 후보 키에 들어 있으므로 비키 속성이 없습니다. 따라서 부분 종속·이행 종속을 일으킬 비키 속성도 없어 2·3정규형 조건을 만족합니다.
③ 3정규형 기준으로 다시 보기: 강사 → 과목에서 강사는 슈퍼키가 아니지만 과목이 후보 키 (학생, 과목)에 포함되므로 허용됩니다.
④ BCNF 검사: 강사는 슈퍼키가 아니므로 BCNF 위반입니다. 실제로 '강사 김 → 통계'라는 사실이 그 강사의 수강생 수만큼 반복됩니다.
⑤ 분해: (강사, 과목)과 (학생, 강사)로 나누면 두 표 모두 BCNF입니다. 첫 표의 키는 강사, 둘째 표의 키는 (학생, 강사)입니다.

표를 나눌 때 확인할 성질이 두 가지 있습니다. 나눈 표를 공통 열로 다시 조인했을 때 원래 행이 더 생기거나 빠지지 않고 정확히 복원되는 무손실 분해는 반드시 지킵니다. 공통 열이 나눈 표 중 한쪽의 슈퍼키이면 무손실입니다(위 예에서 공통 열 강사는 (강사, 과목)의 키). 원래 함수 종속을 나눈 표 하나 안에서 검사할 수 있는 종속성 보존은 3정규형까지는 무손실과 함께 항상 맞출 수 있지만, BCNF에서는 포기해야 할 때가 있습니다. 위 분해에서 (학생, 과목) → 강사는 어느 한 표만으로 검사할 수 없습니다. 그래서 실무에서는 3정규형에서 멈추기도 합니다.

표를 나눌 때는 원래 질문에 필요한 정보를 기본 키와 외래 키로 다시 연결할 수 있어야 합니다. 이 예의 항목에서 참조하는 상품은 정확히 하나이고, 주문도 정확히 하나입니다. 주문, 고객, 상품의 속성을 읽어도 원본 항목 한 줄에 필요한 짝은 표마다 하나씩입니다.

현재 정가와 실제 거래 가격을 함께 읽기

상품 11의 현재 정가를 6,000원에서 6,500원으로 수정합니다. 주문에서 기록한 unit_price_won은 주문 시점에 적용한 거래 단가입니다. 주문항목의 과거 값을 수정하지 않아 그 당시 총액을 다시 계산할 수 있습니다.

실행 예제

import sqlite3

with sqlite3.connect(":memory:") as db:
    db.execute("PRAGMA foreign_keys = ON")
    db.executescript("""
    CREATE TABLE customers (
        customer_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL
    );
    CREATE TABLE orders (
        order_id INTEGER PRIMARY KEY,
        customer_id INTEGER NOT NULL REFERENCES customers(customer_id),
        order_date TEXT NOT NULL,
        status TEXT NOT NULL CHECK (status IN ('paid', 'pending')),
        total_won INTEGER NOT NULL CHECK (total_won >= 0),
        coupon_won INTEGER CHECK (coupon_won >= 0)
    );
    CREATE TABLE products (
        product_id INTEGER PRIMARY KEY,
        name TEXT NOT NULL,
        list_price_won INTEGER NOT NULL CHECK (list_price_won >= 0)
    );
    CREATE TABLE order_items (
        order_id INTEGER NOT NULL REFERENCES orders(order_id),
        line_no INTEGER NOT NULL,
        product_id INTEGER NOT NULL REFERENCES products(product_id),
        qty INTEGER NOT NULL CHECK (qty > 0),
        unit_price_won INTEGER NOT NULL CHECK (unit_price_won >= 0),
        PRIMARY KEY (order_id, line_no)
    );
    """)
    db.executemany("INSERT INTO customers VALUES (?, ?)", [
        (1, 'Mina'),
        (2, 'Jun'),
        (3, 'Sol'),
    ])
    db.executemany("INSERT INTO orders VALUES (?, ?, ?, ?, ?, ?)", [
        (101, 1, '2025-01-02', 'paid', 10000, None),
        (102, 1, '2025-01-03', 'paid', 15000, 1000),
        (103, 2, '2025-01-04', 'pending', 12000, None),
        (104, 2, '2025-01-05', 'paid', 15000, 0),
    ])
    db.executemany("INSERT INTO products VALUES (?, ?, ?)", [
        (11, 'notebook', 6000),
        (12, 'pen', 2000),
        (13, 'pouch', 3000),
    ])
    db.executemany("INSERT INTO order_items VALUES (?, ?, ?, ?, ?)", [
        (101, 1, 11, 1, 6000),
        (101, 2, 12, 2, 2000),
        (102, 1, 11, 2, 6000),
        (102, 2, 13, 1, 3000),
        (103, 1, 11, 2, 6000),
        (104, 1, 13, 5, 3000),
    ])

    db.execute(
        "UPDATE products SET list_price_won = ? WHERE product_id = ?",
        (6500, 11),
    )
    prices = db.execute("""
        SELECT i.order_id, p.list_price_won, i.unit_price_won
        FROM order_items AS i JOIN products AS p ON i.product_id = p.product_id
        WHERE p.product_id = ?
        ORDER BY i.order_id, i.line_no
    """, (11,)).fetchall()
    totals = db.execute("""
        SELECT order_id, SUM(qty * unit_price_won)
        FROM order_items GROUP BY order_id ORDER BY order_id
    """).fetchall()
    print("order, current, at sale:", prices)
    print("order totals:", totals)
db.close()

실행 결과

order, current, at sale: [(101, 6500, 6000), (102, 6500, 6000), (103, 6500, 6000)]
order totals: [(101, 10000), (102, 15000), (103, 12000), (104, 15000)]

이 교재의 orders.total_won은 할인 전 항목 합도 함께 기록한 예입니다. 계산 가능한 합을 보관하면 읽기 편할 수 있지만 항목의 금액이 수정될 때 두 값이 엇갈릴 수 있습니다. 읽기 편의나 속도를 위해 이렇게 일부러 중복을 두는 것을 역정규화라고 합니다. 합이 항상 항목에서 결정된다면 필요할 때 계산하는 편이 단순합니다. 별도로 저장한다면 두 값이 계속 일치하도록 쓰는 경로에 규칙이 필요합니다.

한눈에 정리

개념확인할 것
종속어떤 열의 값이 같은지로 다른 값도 정해지는지 확인한다.
정규화사실의 단위에 맞춰 표를 나누고 관계를 복구할 키를 둔다.
1NF · 2NF · 3NF · BCNF원자값 → 부분 함수 종속 없음 → 이행 함수 종속 없음 → 모든 결정자가 슈퍼키.
무손실 분해나눈 표를 조인하면 원래 행이 정확히 복원된다. 종속성 보존은 BCNF에서 포기할 수 있다.
시점현재 상태와 과거 거래에 기록한 값의 뜻을 구분한다.
