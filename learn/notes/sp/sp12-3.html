암호화, 메시지 인증과 재처리 방지의 역할

글자의 뜻을 감추는 것, 내용이 바뀌지 않았음을 확인하는 것, 한 번 처리한 내용을 다시 쓰지 않는 것은 요구 사항이 서로 다릅니다. 가상의 기록 승인 과정을 통해 각각에 필요한 단서를 봅니다.

이 장을 읽고 나면

  • 기밀성, 메시지 인증, 순서 보호를 요구 사항으로 나눌 수 있다.
  • 공유 키 방식의 HMAC과 TLS 인증서가 각각 무엇을 확인하는지 설명할 수 있다.
  • 메시지 인증이 성공해도 순서 번호를 별도로 검사하는 이유를 설명할 수 있다.

간단한 메시지에서 세 가지 성질을 구분하기

공부 기기 두 대가 같은 진행 기록을 동기화한다고 합시다. 기밀성은 전송 중 내용을 다른 사람이 읽기 어렵게 합니다. 무결성은 받아들인 메시지의 내용 변경을 검출할 수 있게 합니다. 메시지 인증은 송신자가 해당 인증 값을 만들 권한이 있는 키를 가졌는지 확인하는 데 쓰입니다. 이와 별개로, 상태를 바꾸는 서비스는 이미 반영한 명령이 두 번 반영되지 않도록 해야 합니다. 공격자가 예전에 가로챈 정상 메시지를 그대로 다시 보내는 것을 재전송 공격(replay attack)이라고 합니다. 메시지가 바뀌지 않았으므로 인증 검사만으로는 막을 수 없습니다.

성질가상 서비스의 요구
기밀성개인 기록의 내용을 전송 중 보호한다.
메시지 인증과 무결성승인된 키로 생성한, 바뀌지 않은 기록을 받는다.
순서와 중복 처리 확인같은 갱신 번호를 두 번 반영하지 않는다.

HMAC은 메시지와 공유 비밀 키로 인증 태그를 만들어 내용과 공유 키의 사용을 확인하는 표준 방식입니다. 이 경우 메시지 자체는 암호화되지 않습니다. 비밀 키를 가진 장치들이 태그를 만들 수 있으므로, 이 방법만으로 그 장치들 중 하나를 특정할 수는 없습니다.

대칭 키, 공개 키, 서명과 인증서

HMAC처럼 양쪽이 같은 비밀 키를 쓰는 방식을 대칭 키 방식이라고 합니다. 대칭 키 암호(예: AES)는 같은 키로 암호화와 복호화를 하므로 빠르지만, 처음 만나는 두 쪽이 그 키를 어떻게 안전하게 나눠 가질지가 문제로 남습니다. 공개 키 방식은 키를 한 쌍으로 만듭니다. 공개 키는 누구에게나 알려도 되고, 짝이 되는 개인 키는 주인만 가집니다.

도구키확인해 주는 것
대칭 키 암호양쪽이 같은 비밀 키기밀성
HMAC양쪽이 같은 비밀 키무결성, “키를 가진 쪽 중 하나가 만들었다”
전자 서명개인 키로 서명, 공개 키로 검증무결성, “그 개인 키의 주인이 만들었다”(검증자는 서명을 만들 수 없음)
키 교환(예: Diffie–Hellman)각자 비밀 값 + 공개한 값도청자가 알 수 없는 공유 비밀을 새로 만듦

서명은 HMAC과 달리 검증하는 쪽이 같은 서명을 만들 수 없으므로 서명한 쪽을 특정할 수 있습니다. 그런데 공개 키 자체가 정말 그 서버의 것인지는 따로 확인해야 합니다. 인증서는 “이 공개 키는 이 도메인 이름의 것”이라는 내용을 인증 기관(CA)이 자기 개인 키로 서명한 문서입니다. 브라우저는 미리 믿기로 정한 CA의 공개 키로 이 서명을 검증하고, 인증서의 이름이 접속한 도메인과 맞는지, 유효 기간 안인지 확인합니다.

더 알아보기 · 합동 산술로 공유 비밀 만들기

Diffie–Hellman 키 교환은 나머지 연산(합동)을 씁니다. 공개 값 p=23, g=5를 정하고, 한쪽은 비밀 a=6으로 5⁶ mod 23=8을, 다른 쪽은 비밀 b=15로 5¹⁵ mod 23=19를 보냅니다. 각자 받은 값을 자기 비밀로 거듭제곱하면 19⁶ mod 23=2, 8¹⁵ mod 23=2로 같은 값 2를 얻습니다. 도청자는 8과 19만 보았으므로 a나 b를 알아내야 하는데, 실제로 쓰는 매우 큰 p에서는 이것이 계산상 어렵다고 여겨집니다. 이 예의 작은 수는 설명용이며 실제 안전성과 무관합니다.

무엇을 순서 검사에 포함하는가

한 기록에 번호와 내용을 함께 적습니다. 순서 검사에 사용할 번호도 인증하는 바이트에 포함해야 합니다. 수신자는 태그가 맞고 번호가 다음에 기대한 값일 때만 수락합니다. 번호별 재처리 여부는 수신자가 알고 있는 상태와 비교해서 결정합니다. 인증 검사에 실패한 기록은 이 상태를 바꾸지 않습니다.

파이썬으로 정상 처리 순서 확인하기

아래 코드는 파일과 네트워크를 사용하지 않는 한 메모리 안의 예제입니다. 고정된 가짜 키와 번호 1, 2의 바이트를 사용합니다. compare_digest는 인증 태그를 비교하는 데 적합한 표준 라이브러리 함수입니다. 이 예제에서는 값 비교와 순서 승인 두 가지를 구별해 출력합니다.

import hmac

key = b"classroom-key-only"

def tag(message):
    return hmac.digest(key, message, "sha256")

first, second = b"1:complete", b"2:review"
first_packet = (first, tag(first))
second_packet = (second, tag(second))
expected = 1
for record, sent_tag in (first_packet, first_packet, second_packet):
    verified = hmac.compare_digest(tag(record), sent_tag)
    number = int(record.split(b":", 1)[0])
    accepted = verified and number == expected
    if accepted:
        expected += 1
    print(f"번호 {number}: 태그 {verified}, 반영 {accepted}")
print(f"다음 번호: {expected}")

실행 결과

번호 1: 태그 True, 반영 True
번호 1: 태그 True, 반영 False
번호 2: 태그 True, 반영 True
다음 번호: 3

동일한 인증 바이트의 태그는 이전과 같습니다. 그래서 중복 기록도 태그 확인 결과는 True이고, 순서 조건에서 거부됩니다. 실제 여러 프로세스가 상태를 함께 바꿀 때는 기록의 적용과 번호 상태 변경을 일관되게 저장해야 합니다.

실제 연결에서는 검증된 프로토콜을 사용한다

HTTPS 단원에서 본 HTTPS는 HTTP를 TLS 위에서 보냅니다. 현재 버전인 TLS 1.3의 핸드셰이크에서 보통 클라이언트가 서버 인증서를 검증하고, 키 교환으로 이번 연결의 대칭 키를 만듭니다. 클라이언트 인증서도 요구하도록 구성할 수 있습니다. 설정된 연결의 레코드에서는 기밀성과 무결성을 제공하는 인증된 암호화(AEAD)를 사용합니다. 각 레코드를 보호하는 데 쓰는 nonce는 키마다 재사용하지 않도록 관리하는 값입니다. TLS 1.3 레코드에서 양쪽은 순서 번호를 독립적으로 관리해 nonce 계산에 사용합니다. 이 장의 가짜 HMAC 기록은 그러한 전송 프로토콜을 대신할 수 없는 상태 처리 예제입니다.

전송 보호와 서비스의 한 번만 반영 요구도 다릅니다. 사용자가 이미 제출한 요청을 새 연결에서 다시 보낼 수 있으므로, 기록 승인 같은 상태 변경에는 서비스가 요청 식별자나 순번을 유지하는 규칙을 정합니다. 암호 모듈을 직접 조합해 새로운 전송 프로토콜을 만드는 대신, 라이브러리가 제공하는 TLS와 인증서 검증으로 연결을 보호합니다.
