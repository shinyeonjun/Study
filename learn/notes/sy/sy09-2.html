같은 캐시 용량에서 충돌을 줄이는 배치

용량이 똑같아도 주소가 같은 자리를 요구하면 반복 접근이 계속 실패할 수 있습니다. 물리 주소의 태그를 계산하고, 직접 매핑과 2-way를 같은 기록에서 비교합니다.

이 장을 읽고 나면

  • 바이트 주소에서 블록 번호·세트 인덱스·태그를 계산합니다.
  • 같은 데이터 용량에서 연관도가 충돌과 적중률에 미치는 영향을 추적합니다.
  • 정의한 접근 모형에서 평균 메모리 접근 지연을 계산합니다.

주소를 세 부분으로 분해합니다

SY02 캐시에서 가까운 주소를 읽으면 같은 블록을 쓰고, 최근 블록이 남아 있으면 다시 쓸 수 있다는 점을 보았습니다. 이번 장의 데이터 캐시에는 16바이트 데이터가 들어가는 라인 네 개를 둡니다. 라인들을 세트로 나눕니다. 주소는 세트 하나를 지정하고 그 세트 안에서만 데이터가 들어갈 자리를 탐색합니다. 세트에 들어가는 라인 수가 연관도 또는 way 수입니다. 이 장의 입력은 이미 변환을 마친 물리 바이트 주소입니다.

주소 a를 블록 크기 B로 나누면 몫 b=⌊a/B⌋가 메모리 블록 번호, 나머지가 오프셋입니다. 세트 수 S로 다시 b를 나누면 나머지 b mod S가 세트 번호이고 몫 ⌊b/S⌋가 태그입니다. 세트가 맞아도 원하는 블록인지 구분할 수 있게 각 라인에 태그를 저장합니다. 비어 있는 라인은 유효하지 않습니다. 저장된 유효 태그와 요청 태그가 일치하면 블록 안의 오프셋으로 원하는 바이트에 접근할 수 있습니다.

예를 들어 주소 68은 4×16+4라 블록 4의 오프셋 4입니다. 세트가 4개면 (태그, 세트)=(1,0), 2개면 (2,0)입니다. 다시 합치면 원래 주소는 (태그×세트 수+세트 번호)×블록 크기+오프셋입니다. B와 S가 2의 거듭제곱일 때는 각각 하위 비트 묶음으로 계산할 수 있습니다.

똑같은 용량에서 왜 다르게 실패하나요?

직접 매핑은 각 세트에 라인이 하나뿐입니다. 네 라인의 직접 매핑 캐시에서 블록 0과 4의 세트 번호는 둘 다 0입니다. 태그가 다르므로 두 블록을 번갈아 읽으면 하나를 가져올 때마다 기존 블록을 밀어냅니다. 동시에 필요한 데이터가 캐시에 충분히 작아도, 들어갈 수 있는 위치가 겹쳐 일어나는 실패가 충돌 미스입니다. 세트마다 두 라인이 있는 2-way 캐시는 세트를 2개로 줄이면 전체 데이터 용량은 같으면서 세트 0에 블록 0과 4를 같이 둘 수 있습니다.

처음 주소 0을 읽고 주소 4를 읽으면 블록 0 안에 같이 들어 있어 공간 지역성으로 적중합니다. 주소 64 뒤에 다시 주소 0을 읽는 부분에서는 2-way에 남은 블록 0을 시간 지역성으로 다시 씁니다. 모든 캐시가 비어 있다고 두었으므로 세 블록 각각의 첫 참조는 두 구조에서 모두 실패합니다. 직접 매핑에서 블록 0과 4에 발생한 두 번의 추가 실패는 배치 제약 때문에 생겼습니다.

세트가 가득 찼을 때 어떤 블록을 교체할지도 결과에 영향을 줍니다. 예제 기록에서는 2-way의 어느 세트도 자신의 라인 수를 넘는 종류를 받지 않습니다. 시뮬레이터를 연장할 수 있도록 예제 코드에는 가장 오래 쓰지 않은 라인을 밀어내는 LRU를 넣었습니다.

실패율뿐 아니라 비용을 함께 씁니다

한 캐시 조회 비용은 항상 4사이클, 실패일 때 더 낮은 계층에서 블록을 가져오는 추가 비용은 30사이클로 둡니다. 요청을 겹치지 않고 처리해 각 요청 비용을 더합니다. 평균 메모리 접근 시간은 기본 조회 비용 + 실패율 × 추가 실패 비용입니다. 직접 매핑은 8회 중 5회 실패하므로 4+(5/8)×30=22.75사이클, 2-way는 3회 실패하므로 4+(3/8)×30=15.25사이클입니다. 실제 구조에서는 더 많은 태그를 비교하면 적중 비용 자체가 달라질 수 있어 같다는 가정을 확인해야 합니다.

trace = [0, 4, 64, 0, 4, 68, 16, 20]
block_bytes, line_count = 16, 4

def replay(ways):
    set_count = line_count // ways
    cache = [[] for _ in range(set_count)]
    history = []
    for address in trace:
        block, offset = divmod(address, block_bytes)
        tag, set_index = divmod(block, set_count)
        assert (tag*set_count + set_index)*block_bytes + offset == address
        lines = cache[set_index]
        if tag in lines:
            history.append("H")
            lines.remove(tag)
        else:
            history.append("M")
            if len(lines) == ways:
                lines.pop(0)
        lines.append(tag)
    return "".join(history)

for ways in (1, 2):
    history = replay(ways)
    hits = history.count("H")
    misses = len(history) - hits
    average = 4 + 30*misses/len(history)
    print(f"{ways}-way", history, "hit/miss", hits, misses, "cycles", average)
1-way MHMMHMMH hit/miss 3 5 cycles 22.75
2-way MHMHHHMH hit/miss 5 3 cycles 15.25

시뮬레이터는 태그의 리스트를 오래 전에 쓴 것에서 최근에 쓴 것 순으로 유지합니다. 파이썬 리스트에서 이 작업에 걸린 시간은 대상이 아닙니다. 관측 대상은 주어진 주소 기록을 처리한 적중 횟수와 접근 모형의 비용입니다.

핵심어기억할 기준
주소 분해블록 번호를 세트 수로 나눈 몫이 태그이고 나머지가 세트 번호입니다.
연관도한 세트에 저장 가능한 라인 수이며, 같은 세트로 몰리는 블록의 충돌을 줄일 수 있습니다.
평균 접근 시간항상 드는 조회 비용에 실패율과 추가 비용의 곱을 더합니다.
